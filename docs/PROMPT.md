Он самодостаточен: новая сессия не должна зависеть от истории предыдущего диалога.

## 1. Быстрый контекст проекта (передаётся новому агенту)

- **Что это:** распределённый узел хранения DAG-графа транзакций поверх консенсуса Raft.
- **Стек:** Rust (edition 2024), tokio, axum 0.7, openraft 0.10 (git databendlabs), redis 0.32, rayon, ed25519-dalek + base58, blake3, serde/serde_json, clap, tracing, reqwest.
- **Зрелость:** экспериментальный прототип / ранний MVP. Компилируется, но хранилища in-memory, валидация в state machine выключена заглушками, секреты в коде.
- **Ключевые файлы:**
  - `src/main.rs` — точка входа, CLI (`--id`, `--addr`, `--port`).
  - `src/lib.rs` — `TypeConfig`, `start_raft`, тип `Tx`.
  - `src/server.rs` — HTTP-хендлеры (add/remove/pool/full/genesis), валидация `validate_and_prepare_tx`.
  - `src/processor.rs` — фоновая очистка «тяжёлых» узлов.
  - `src/raft/` — `log.rs`, `store.rs`, `network.rs`, `router.rs`, `api.rs`, `command.rs`.
  - `src/graph/` — `dag.rs` (структура DAG), `weights.rs` (глубины/веса).
  - `to/` — мёртвые черновики (не собираются, не трогать без причины).
- **Документы аудита и плана:** `docs/AUDIT.md`, `docs/tz/README.md`, `docs/tz/01-critical.md` … `04-missing.md`.
- **Заготовки, созданные заранее (использовать, а не создавать заново):**
  - `.env.example` — шаблон конфигурации окружения → задача **K1**.
  - `.gitignore` (уже расширен: `.env`, `/data`, логи, дампы Redis) → задача **D2**.
  - `Dockerfile` и `docker-compose.yml` (кластер из 3 узлов + Redis) → задача **D2**.
  - `.github/workflows/ci.yml` (fmt + clippy `-D warnings` + build + test) → задача **V9**.
    Внимание: CI намеренно строгий и **сейчас падает на clippy-предупреждениях** — это ожидаемо
    до выполнения **D1**. Не «чините» CI ослаблением правил, чините предупреждения.

## 2. Мастер-промпт (копировать в новую сессию)

> Ты продолжаешь работу над Rust-проектом `dagdb` в `/home/pin/dev/yat/srv` — распределённым DAG-сервером на Raft (openraft + axum + Redis).
>
> **Сначала прочитай и прими как источник истины:**
> - `docs/AUDIT.md` — результаты аудита (находки S*, D*, C* с характерами 🔴/🟠/🟡/🔵).
> - `docs/tz/README.md` — сводный трекер задач и зависимости.
> - `docs/tz/<ФАЙЛ_ТЗ>` — ТЗ блока, который будем реализовывать.
>
> **Задача этой сессии:** реализовать задачи `<ID-СПИСОК>` из `<ФАЙЛ_ТЗ>` строго по описанию в ТЗ.
>
> **Правила работы (обязательны):**
> 1. Не выдумывай требования сверх ТЗ; при неоднозначности — уточняй у меня, а не догадывайся.
> 2. Перед изменениями исследуй существующий код и следуй его стилю, именованию и структуре модулей.
> 3. Работай по одной задаче: реализовал → проверил → отметил в трекере → перешёл к следующей. Не смешивай несвязанные изменения в один шаг.
> 4. После каждой задачи запускай: `cargo fmt`, `cargo clippy --all-targets`, `cargo test` (добавляй тесты, если задача их требует). Всё должно быть зелёным.
> 5. Не коммить и не удалять чужие/незакоммиченные изменения (`to/`, экспериментальные файлы) без явного разрешения.
> 6. Не храни секреты в коде; всё конфигурируемое — через env/CLI.
> 7. После завершения задач обнови статусы в `docs/tz/README.md` (⬜ → ✅) и добавь краткую запись о фактических изменениях.
> 8. По ходу работы веди краткий журнал: что изменено, какие файлы, какие проверки пройдены, какие решения приняты и почему.
>
> **Формат отчёта в конце сессии:**
> - Список выполненных ID и их статус.
> - Изменённые/созданные файлы.
> - Результаты `fmt`/`clippy`/`test`.
> - Отклонения от ТЗ и причины.
> - Что осталось и что рекомендуется делать в следующей сессии.
>
> **Начни с:** чтения `docs/tz/<ФАЙЛ_ТЗ>` и вывода краткого плана задач `<ID-СПИСОК>` перед началом правок.

## 3. Инварианты проекта (нельзя ломать)

- Детерминированность state machine: одинаковая команда → одинаковое состояние на всех репликах.
- Валидация транзакции должна быть одинаковой на всех узлах и не зависеть от сети/времени.
- `func` входит в подписываемый и хэшируемый контент.
- Хэш узла уникален; повторная вставка запрещена.
- Удалённые узлы попадают в реестр `added`; `is_node_added` должен переживать снапшот/рестарт.
- Публичный API и внутренний (Raft/mng) API разделены.

## 7. Соглашения

- **Коммиты (Conventional Commits):** `type(scope): summary`, где type ∈ {feat, fix, refactor, test, docs, chore, perf, security}. Пример: `security(config): load redis url from env`.
- **Ветки:** `feat/<block>-<short>`, `fix/<short>`, `security/<short>`.
- **Порядок коммитов:** не смешивать форматирование/рефактор с логикой в одном коммите.
- **Ссылки на находки:** в описании коммита указывать ID из ТЗ (например, `Refs: K1`).
- После завершения блока обновлять трекер `docs/tz/README.md` отдельным `docs:` коммитом.
