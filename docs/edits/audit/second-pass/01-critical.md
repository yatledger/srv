## 1. Цель

Устранить проблемы, которые ломают корректность контракта системы или целостность данных.

## 3. Технические требования

- **K1 (C34).** `Raft::client_write` возвращает `Ok(ClientWriteResponse)`, даже если `apply` вернул
  прикладную ошибку: она лежит в `response.data.value = Some("Error: ...")` (успех — `Some("Ok")`).
  Проверить payload во всех точках записи: `src/server.rs:263` (`add_handler`),
  `src/cleanup.rs:129` (`archive_and_remove`), `src/server.rs:630` (`load_genesis`).
  При `Error` возвращать клиенту `4xx` (конфликт: узел/родитель) и писать `audit result=error`.
  Дополнительно ввести типизированный `Response`/`ApplyResult` (см. C43), чтобы ошибку нельзя было
  проигнорировать снова.
- **K2 (C35, S15).** `load-genesis` обязан сверять переданный `hash` с `ordered_sum(&tx, &func)` и
  проходить те же проверки структуры/подписи/родителей, что `POST /add` (либо быть явно
  административной операцией с честной документацией). Хэши в `genesis.json` в текущем виде
  каноническому хэшу содержимого **не соответствуют** (пересчёт не совпадает ни с `func`, ни без
  него) — перегенерировать файл канонически.

## 4. Критерии готовности (Definition of Done)

- Запись, отвергнутая state machine, возвращает клиенту ошибку, а не `200`; в аудит-логе
  `result=error`.
- `load-genesis` не принимает транзакцию с несовпадающим/неканоническим хэшем.
- Есть регрессионный тест: `apply` с отсутствующим родителем через публичный путь даёт `4xx`.
