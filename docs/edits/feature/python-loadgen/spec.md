### Что решено наводящими вопросами (2026-10-09)

- **Роль** — Python-бот становится **внешним HTTP-клиентом к уже запущенному кластеру**
  (локальному или удалённому). Он **не** поднимает in-process кластер и **дополняет**, а не дублирует
  Rust-инструмент `N01` (`loadgen`).
- **Хэш/подпись** — владелец предоставил код `ordered_sum`/`sign_message`; по итогам сверки (см. §2.3)
  канонический хэш и подпись **портятся из `src/utils.rs`** прямо в `python/`, без зависимости от
  внешнего `src.utils`.
- **Ключи** — владелец выбрал закоммитить `python/keys.py` с ключами `sk`/`pk` (см. риск в §5).
- **Объём** — корректная генерация tx + отчёт/проверка консистентности + рефакторинг/чистка + CLI.
- **`var.ca`** — адрес отправителя (не хардкод `"00000"`).
- **E2E** — прогон на реальном кластере в Docker (Redis + узлы `21001..21004`).

## 2. Проблема и сценарий

### 2.1. Формулировка владельца (дословно)

> «у меня есть такой код: … это бот для нагрузочного тестирования. я хочу его протестировать на
> кластере, доработать, переработать, убрать лишнее, добавить недостающее. потом сохранить в папке
> python по моему согласию.»

### 2.2. Проблема

Владелец использует внешний Python-скрипт для нагрузки на кластер. Скрипт **не запускается и не
проходит валидацию** против текущего `dagdb`. Ключевые дефекты (проверено по коду):

| # | Дефект | Последствие |
|---|---|---|
| 1 | `HOST = random.choice([...])` внутри `run_sender` возвращает **строку**, затем `HOST[i]` индексирует символ | В `send` уходит URL из одного символа (`'h'`, `'t'`…) — **все** запросы падают, нагрузка нулевая |
| 2 | `ordered_sum` не добавляет `func`, конкатенирует значения **без разделителей**, сортирует только один уровень | Строка не совпадает с каноничной из `utils.rs` |
| 3 | `sign_message` делает **второй** blake3 и подписывает этот digest | Узел подписывает **сырой** digest `blake3(canonical)` — подпись не проходит `verify_signature` |
| 4 | `seq = random.randint(0, 100000)` | Нарушает инвариант **V18** (строгий рост `seq` на адрес) → прикладной отказ почти всех tx |
| 5 | `prnts = все узлы пула` | При `|pool| > 100` отказ `validate_parents` (2..100) |
| 6 | Дефолтный `PUBLIC_RATE_LIMIT_PER_SEC=50` | Поток `429`, часть валидных tx не проходит |
| 7 | 4 «реалистичных» генератора, 3 не используются | ~300 строк мёртвого кода |
| 8 | Нет отчёта (accepted/rejected по причинам, латентность, консистентность реплик) | Нельзя судить о корректности прогона |
| 9 | Нет CLI/конфигурации (всё хардкод) | Невоспроизводимость |
| 10 | `from src.utils.data import ordered_sum` — внешний несуществующий пакет | Импорт падает в этом репозитории |

### 2.3. Эмпирическое подтверждение несовместимости хэша/подписи

Сверка кода владельца с `src/utils.rs` (итерация 2026-10-09):

- Ключи `sk[i]`/`pk[i]` **корректны**: `base58(SigningKey(sk[i]).verify_key) == pk[i]`.
- Для контрольной tx `{prnts:[aaa,bbb], addr:pk0, seq:1, var:{ca:pk0,to:pk1,val:100,msg:"hello"}}`:
  - канонический хэш узла (Rust, `ordered_sum(tx,"transferToken")`) =
    `0d5636a3c5dabbaccf44136a38c59e627bf87d5d5103e4053192a3e5b77c01af`;
  - подпись бота проверена узлом против этого хэша → **`BadSignatureError`**.
- Верный порт `canonical_json + blake3` на Python **побайтово** воспроизвёл `0d5636a3…`
  (сверено временным Rust-тестом, удалён после проверки). Исправленная подпись (ed25519 над **сырым**
  32-байтным digest, hex) узлом **принимается**.

Вывод: §2.2 п.2–3 — не косметика, а блокирующий дефект; без порта канонического хэша бот бесполезен.

### 2.4. User story / кейсы

1. Как **разработчик/дежурный**, я хочу запустить Python-нагрузчик одной командой против работающего
   кластера (локального или удалённого) и получить отчёт: сколько валидных tx принято/отклонено
   (с причинами), достигнутый TPS, перцентили задержки, и совпадает ли итоговый размер DAG на репликах.
2. Как **владелец**, я хочу, чтобы нагрузка строилась по тем же правилам, что применяет state machine
   (монотонный `seq`, 2..100 живых родителей, канонический хэш/подпись как в `utils.rs`), а не копией
   логики, которая расходится.
3. Как **разработчик**, я хочу воспроизводимый прогон (`--seed`) и машинно-читаемый JSON-отчёт для CI.

**Успех:** инструмент запускается, генерирует валидные транзакции, все принятые tx консистентны на
всех репликах, отчёт печатается в консоль/JSON; код возврата нулевой при выполнении корректностных
инвариантов.

## 3. Требования

### 3.1. Функциональные

- **R1. Внешний клиент.** `python/` — самостоятельный инструмент, работающий против уже запущенного
  кластера по публичному HTTP (`POST /`, `GET /pool`, `GET /full`, `GET /health`). Кластер не поднимает.
- **R2. Единый источник истины по хэшу/подписи.** Канонический хэш — порт `canonical_json` из
  `src/utils.rs` (рекурсивная сортировка ключей, порядок массивов сохраняется, экранирование строк как
  в `serde_json`), `func` добавляется в контент; `hash = blake3(canonical)`; `sign` — ed25519 над
  **сырыми байтами хэша**, hex. Ключи — base58.
- **R3. Валидная нагрузка.** `prnts` — `k` **живых** узлов из `/pool`, `2 ≤ k ≤ min(100, |pool|)`;
  `seq` — **строго монотонный на адрес** (у каждого аккаунта свой счётчик, с 1); `func=transferToken`;
  `var = {ca: <addr отправителя>, to: <addr>, val ≥ 0, msg ≤ 2500}`.
- **R4. Конфигурация (CLI).** Хосты (список), число tx **или** длительность, целевой TPS, конкурентность,
  число аккаунтов, диапазон/число родителей, seed, путь JSON-отчёта, опц. `--internal-token` (для
  внутренних ручек, если понадобятся), verbose.
- **R5. Устойчивость.** Обработка `429` (пауза/backoff, повтор), таймаутов и недоступных узлов
  (переключение на другой из списка), `503` (нет лидера — ретрай). Никаких «тихих» потерь запроса.
- **R6. Отчёт и корректность.** Печатает: принято/отклонено с разбивкой по причинам (текст `message`
  из `4xx`), достигнутый TPS, p50/p95/p99 задержки клиента, итоговый `total` из `/full` по каждому узлу.
  **Корректностные инварианты (влияют на код возврата):** нет прикладных отказов у заведомо валидных tx;
  `total` одинаков на всех репликах. Throughput/латентность — информационные (без SLA).
  JSON-отчёт: `{ params, accepted, rejected:[{reason,count}], achieved_tps, latency_ms:{p50,p95,p99},
  dag_total_per_node:{node:total}, ok, errors:[] }`.
- **R7. Воспроизводимость.** При фиксированном `--seed` параметры транзакций воспроизводимы
  (фактическая задержка Raft — нет).
- **R8. Чистка.** Убрать мёртвые генераторы (`realistic`, `advanced`, `simple`), оставить один
  настраиваемый; разнести на модули; единый вход `python -m loadgen`.
- **R9. Документация.** `python/README.md` (запуск/параметры/ограничения) + запись в `docs/edits/feature/`.

### 3.2. Не-функциональные

- Инструмент **не входит** в `cargo test --all` и не влияет на сборку Rust.
- Никаких изменений `src/`, `Cargo.toml`, схемы состояния, `SCHEMA_VERSION`, публичного API.
- Секреты: `python/keys.py` (решение владельца) — с явной пометкой риска; предусмотреть возможность
  подстановки ключей из окружения.

## 4. Границы и не-цели

**Входит:** перенос на Python под этот репозиторий; корректный канонический хэш/подпись; корректная
генерация tx; CLI/конфиг; устойчивость (rate limit/недоступность); отчёт + проверка консистентности;
рефакторинг и чистка; юнит-тесты; `python/README.md`.

**MVP:** корректный один генератор + external-режим + базовый отчёт (accepted/rejected/причины, TPS) +
JSON + юнит-тесты на хэш/seq/выбор родителей. **Полный вариант:** перцентили задержки, проверка `/full`
по всем узлам, retry/backoff, опц. внутренние ручки по токену.

**Не-цели (осознанно вне скоупа):**

- Не поднимаем in-process кластер и не дублируем `N01` (`loadgen`) — Python работает **внешним**
  клиентом.
- Не восстанавливаем «реалистичные» генераторы исходника (тренды/суточный множитель/микрокластеры).
- Не реализуем TLS/распределённую нагрузку с нескольких машин, не измеряем CPU/RSS узлов.
- Не меняем Rust-код/публичный API/схему состояния.
- Не добавляем Python-нагрузку в обязательный PR-CI (кандидат в отдельную задачу, как и `N01.4`).

## 5. Влияние

- **Инварианты (`AGENTS.md` §6).** Инструмент **использует** инварианты, не меняет их: канонический
  хэш/подпись — порт `utils.rs` (сверен побайтово); монотонный `seq` — соблюдается генератором;
  уникальность хэша — уникальным `seq`/содержимым; разделение API — бьём в публичные ручки `POST /`,
  `/pool`, `/full`.
- **Совместимость.** Аддитивно: новых полей состояния/команд/версий схемы нет. `docs/api/`,
  `Cargo.toml`, `.env.example` не меняются.
- **Секреты.** ⚠️ Решение владельца — закоммитить `python/keys.py` с `sk`/`pk`. Это **отклонение** от
  правила «секреты только из env» (`AGENTS.md` §4/§5) и риск утечки в историю git. Ключи —
  тестовые/дев-стенд; предусматриваем override из окружения и пометку в `python/README.md`.
- **Зависимости.** Python: `httpx`, `pynacl`, `blake3`, `base58`; тесты — `pytest`. Версии фиксируем в
  `python/requirements.txt`. (Именно эти библиотеки делают хэш/подпись совместимыми с Rust.)
- **Производительность/безопасность.** Инструмент клиентский, изолирован; запуск против удалённого
  кластера — на усмотрение владельца (недоверенные среды прогонять осознанно).

## 6. Связи

- **N01 / `feature/load-generator`** — родственный Rust-инструмент (in-process кластер). Python —
  внешний комплементарный клиент; `N01` §«не-цели» прямо оставлял Python-скрипт владельца нетронутым —
  эта задача закрывает его.
- **V18/C45** (`docs/edits/audit/second-pass/02-important.md`) — монотонный `seq`; главная причина
  несовместимости исходного бота.
- **K1/C34** — прикладной отказ SM доходит до клиента `4xx` (`{"status":"error","message":...}`);
  инструмент использует это для классификации причин.
- **V15/C38** — родители только из живого DAG ⇒ источник — `/pool`, не `added`.
- **Q2/C41** — `/pool`, `/full` не держат лок (важно для параллельной генерации).
- **F1/F2** (`docs/edits/fix/redis-startup-hang`, `http-port-ignored`) — учтены при подъёме кластера
  для E2E.
- Конфликтов с реализованными фичами/фиксами нет.
