## 2. Проблема и сценарий

### 2.1. Формулировка владельца (дословно)

> «ещё я хочу получать красивые логи с нод в духе "нода N получила / переправила / записала
> транзакцию (хэш)"»

Уточнения (наводящие вопросы 2026-10-09):

1. **Область** — core-события на узлах (`server.rs`, `raft/store.rs`) + интеграция в вывод `loadgen`.
2. **«записала»** — пишется на **каждой** реплике (видна репликация по всем узлам).
3. **В loadgen** — события узлов идут в **stderr** на `info`, чтобы не ломать пофреймовый вывод и
   отчёт в stdout.

### 2.2. Проблема

В потоке записи узлы почти не «рассказывают» о происходящем человекочитаемо: `add_tx`/`add_handler`
пишут в лучшем случае `debug!`, а применение в state machine — только `debug! replicate to sm` и
`warn!` при отказе. При наблюдении за кластером (в т.ч. через `loadgen`) не видно, какой узел принял
запись, какой перенаправил её лидеру и какие реплики её применили.

### 2.3. User story / кейсы

1. Как **владелец/разработчик**, я хочу видеть в логах живую картину: `нода 2 получила транзакцию …`,
   `нода 2 переправила транзакцию … на адрес …`, `нода N записала транзакцию …`.
2. Как **пользователь `loadgen`**, я хочу, чтобы эти события были наглядными и не ломали пофреймовый
   вывод/отчёт.

**Успех:** при нагрузке в логах видны события трёх видов; «записала» появляется на всех репликах;
в `loadgen` события идут в stderr и не смешиваются с цветным stdout-выводом.

## 3. Требования

### 3.1. Функциональные

- **R1. «получила».** На входе публичного `POST /` (`add_tx`) узел-приёмник логирует
  `нода {id} получила транзакцию {хэш}` (один раз на успешно подготовленную к записи tx).
- **R2. «переправила».** Если узел не лидер и форвардинг лидеру успешен, логирует
  `нода {id} переправила транзакцию {хэш} на адрес {leader_addr}`.
- **R3. «записала».** В `raft/store.rs::apply` **каждая** реплика, успешно применившая `Add`,
  логирует `нода {id} записала транзакцию {хэш}`.
- **R4. Короткий хэш.** Во всех событиях — сокращённый хэш (`head…tail`, `utils::short_hash`), чтобы
  строки были читаемыми.
- **R5. Уровень и вывод.** События — уровень `info`. В `loadgen` лог-подписчик пишет в **stderr**
  компактным форматом без span-контекста; пофреймовый вывод и отчёт остаются в stdout.
- **R6. Тишина по умолчанию у шумных библиотек.** Внутренний `openraft`-шум bootstrap
  (`membership_log_id changed: …`) приглушается (`openraft=error`), чтобы не засорять события узлов.
- **R7. Управляемость.** `RUST_LOG` сохраняет приоритет; `--verbose` повышает дефолт до `debug`.

### 3.2. Нефункциональные

- **Детерминизм.** Логирование не влияет на state machine: `node_id` в `StateMachineStore` — только
  для сообщения, на состояние/сериализацию не влияет; порядок применения и результат не меняются.
- **Инварианты (`AGENTS.md` §6)** — не затрагиваются: канонический хэш/подпись, формат состояния,
  `SCHEMA_VERSION`, Raft-контракт, публичный/внутренний API не меняются.
- **Отсутствие новых зависимостей.** Время — через `tracing-subscriber` `ChronoLocal`; форматтер —
  рукописный `FormatEvent`.

## 4. Границы и не-цели

**Входит:** события «получила/переправила/записала», `utils::short_hash`, `log_filter::default_filter`
(общий дефолт `info` + приглушение `openraft`), компактный stderr-форматтер в `loadgen`, `node_id` в
`StateMachineStore`, обновление `README.md` и юнит-тестов.

**Не-цели:** структурные JSON-поля событий, изменение HTTP-контракта/`ApiResponse`, метрики, TUI,
изменение Python-нагрузчика, рефакторинг серверной логики; события `Remove`/membership не логируются
(только транзакции `Add`).

## 5. Влияние

- **Инварианты.** Логи — представление; `SCHEMA_VERSION`/Raft-контракт/API не меняются. `node_id`
  в state machine не сериализуется (в `StateMachineData` не входит).
- **Совместимость.** Аддитивно. Дефолтный уровень основного бинарника поднят `info` (без `openraft`-шума);
  `RUST_LOG`/`--verbose` управляют как прежде.
- **Эксплуатация/данные.** Логи идут в stderr (loadgen) / stdout (dagdb); на диск/нагрузку не влияют.
