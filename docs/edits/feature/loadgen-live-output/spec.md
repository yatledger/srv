## 2. Проблема и сценарий

### 2.1. Формулировка владельца (дословно)

> «я хочу чтобы src/bin/loadgen во время тестирования выводил содержимое запросов и ответов на
> экран в красивом формате. при запуске без параметров, пусть между запросами будет рандомный
> sleep 0.1 до 2.5 секунд. --sleep можно указать в том числе 0. просто нужно сделать
> презентабельно, чтоб было интересно тестировать )»

Уточнения, полученные в наводящих вопросах (2026-10-09):

1. **Включение вывода** — авто-режим **при запуске без параметров**; с любым явным флагом работает
   прежнее поведение (кроме явного `--show-tx`).
2. **Пейсинг без параметров** — случайная пауза, TPS **выключен**; явный `--tps` или `--sleep`
   задаёт своё.
3. **`--sleep SECS`** — фиксированная пауза в секундах (в т.ч. `0` — выключить); без флага в
   демо-режиме — случайная пауза `0.1..2.5` с.
4. **Формат** — цветной многоблочный (ANSI, авто-определение TTY, **без новых зависимостей**):
   на каждую транзакцию «шапка → запрос → ответ».
5. **Конкурентность** — в демо-режиме (без параметров) `--concurrency 1` (§3.3), чтобы поток был
   ровным и легко наблюдаемым.
6. **Скоуп** — CI и `--json-out` **не трогаем**; дефолты `--nodes`/`--tx`/`--concurrency` (вне демо)
   не меняем.

### 2.2. Проблема

Сейчас `loadgen` пишет только итоговый отчёт (`report::print_report`) и технические `eprintln!` под
`--verbose`. Для ручного/демонстрационного прогона это «чёрный ящик»: не видно, какие именно
транзакции уходят (`prnts`, `addr`, `seq`, `var`, `sign`), какой пришёл ответ (статус, задержка,
причина отказа) и как запросы чередуются во времени. Владелец хочет **интересный, презентабельный**
режим наблюдения: медленный (`0.1..2.5` с между запросами) поток с наглядным пофреймовым выводом.

`--tps 500` (дефолт) при демонстрации слишком быстр: за секунды пролетают сотни транзакций, читать
вывод невозможно, а случайная пауза как раз создаёт «живой» темп.

### 2.3. User story / кейсы

1. Как **владелец/разработчик**, я хочу запустить `loadgen` вообще без аргументов и увидеть
   замедленный поток: на каждую транзакцию — цветной блок с запросом и ответом, — чтобы наглядно
   наблюдать работу кластера и получать удовольствие от тестирования.
2. Как **разработчик**, я хочу управлять темпом: `--sleep 0.5` (фиксированная пауза), `--sleep 0`
   (без паузы, максимальная скорость), отсутствие флага (демо — случайная пауза).
3. Как **CI/автоматизация**, я хочу, чтобы обычный и JSON-прогон **не** печатали пофреймовые блоки и
   не замедлялись: `--json-out` и job `load` работают как раньше.

**Успех:** запуск без параметров даёт наглядный медленный поток цветных блоков; явные флаги
сохраняют прежнее воспроизводимое поведение; корректностные инварианты и код возврата не меняются.

## 3. Требования

### 3.1. Функциональные

- **R1. Авто-демо-режим.** Если процесс запущен **без аргументов** (`std::env::args_os().len() == 1`),
  включаются: наглядный вывод (`--show-tx`), случайная пауза `0.1..2.5` с, TPS = 0 (без пейсинга),
  конкурентность = 1 и **ограничение по времени `--duration-sec 60`** (вместо бюджета `--tx 500`),
  чтобы демо было обозримым. Любой переданный флаг отключает авто-демо (действуют явные значения и
  обычные дефолты).
- **R4a. Случайный узел-приёмник.** Каждый запрос отправляется на случайный узел кластера (не
  обязательно лидер); не-лидер перенаправляет запись лидеру. Родители берутся из `/pool` **того же
  узла**, чтобы его ранняя проверка состояния не отклонила валидную транзакцию из-за отставания
  реплики. В блоках вывода виден узел и роль (`лидер` / `follower → лидер`).
- **R2. Флаг `--show-tx`.** Включает пофреймовый вывод запроса и ответа. По умолчанию `false`;
  в демо-режиме — `true`. Вывод идёт в **stdout** (итоговый отчёт — как есть).
- **R3. Флаг `--sleep <SECS>`.** Тип `f64` (дробные секунды), допускается `0`; отрицательные и
  `NaN` отклоняются с понятной ошибкой. `0` = пауза выключена. Без флага: демо → случайная
  `0.1..2.5` с; вне демо → паузы нет.
- **R4. Пофреймовый формат.** На каждую финальную попытку отправки — один связный блок:
  - **шапка:** сквозной номер запроса, `worker`, `seq`, адрес-отправитель (кратко);
  - **запрос:** целевой URL/лидер, `func`, `prnts` (число + сокращённые хэши), `var` (`to`/`val`/`msg`
    кратко), `sign` (сокращённо);
  - **ответ:** HTTP-статус (+ reason-фраза), задержка клиента в мс, при `4xx`/`5xx` — причина.
  - Цвет: успех — зелёный, отказ — красный, структурные линии — приглушённые.
- **R5. ANSI и авто-TTY.** Цвета включаются только если stdout — терминал (иначе — чистый текст без
  ESC-последовательностей). Учитывать `NO_COLOR`. **Без новых crate.**
- **R6. Целостность блока.** При `--concurrency > 1` блоки не перемешиваются: вывод одного блока
  атомарен (общий мьютекс вывода). В демо-режиме `concurrency = 1`, поэтому поток ровный.
- **R7. Совместимость с ретраями.** Печатается итог последней попытки; служебные ретраи
  (`503`/5xx/сеть) не печатают отдельные блоки (в `--verbose` остаются технические логи).
- **R8. Неизменность результата.** Печать не влияет на генерацию (`seq`, `prnts`, подпись),
  корректностные инварианты, код возврата, `--json-out` и CI-job `load`.

### 3.2. Нефункциональные

- **Детерминизм.** Случайная пауза использует **отдельный** ГПСЧ, чтобы не сдвигать поток параметров
  транзакций: при одном `--seed` параметры tx воспроизводимы независимо от наличия/значения паузы.
- **Инварианты (`AGENTS.md` §6)** — не затрагиваются: используется существующий `POST /` и `/pool`;
  канонический хэш/подпись/`SCHEMA_VERSION`/Raft-контракт/публичный API не меняются.
- **Производительность.** `--show-tx` — человеческий режим; в CI он не включён. Печать под мьютексом
  не влияет на корректность, но ускоряемый прогон с `--json-out` остаётся без пофреймового вывода.
- **Отсутствие новых зависимостей.** Цвета — рукописные ANSI-последовательности (без `owo-colors`/
  `colored`/`console`); не трогаем `Cargo.toml`.

## 4. Границы и не-цели

**Входит:** авто-демо-режим (без аргументов), флаг `--show-tx`, флаг `--sleep` (в т.ч. `0` и
случайный демо-диапазон), пофреймовый цветной вывод запроса/ответа, атомарность блоков, обновление
`README.md`, юнит-тесты форматтера/резолвинга.

**Не-цели (осознанно вне скоупа):**

- Не меняем `--nodes`/`--tx`/`--concurrency` (вне демо), `--tps` (вне демо-режима), `--json-out` и
  job `load` в CI.
- Не добавляем новые зависимости (в т.ч. TUI/`ratatui`, progress-bar crate, `indicatif`).
- Не делаем интерактивный TUI, графики, live-таблицу, звуки.
- Не трогаем Python-нагрузчик `N02` и публичный HTTP-API (`docs/api/`) — изменений нет.
- Не меняем in-process кластер, bootstrap, корректностные инварианты и код возврата.

## 5. Влияние

- **Инварианты (`AGENTS.md` §6).** Инструмент по-прежнему **использует** инварианты, не меняет их;
  печать — только представление уже отправленных запросов. Канонический хэш/подпись и монотонный
  `seq` не затрагиваются.
- **Совместимость.** Аддитивно: новые CLI-флаги. Значения по умолчанию вне демо-режима сохранены
  (поведение прежних скриптов/CI не меняется). `docs/api/`, `openapi.json`, `.env.example`,
  `Cargo.toml` — без изменений.
- **Взаимодействие пейсингов.** Пауза `--sleep` и целевой TPS — ортогональны: в демо TPS выключен
  (`0`), поэтому темп задаёт только пауза; при явном `--tps` без `--sleep` работает прежний пейсинг.
  При одновременном `--tps` и `--sleep N` действуют оба (пер-workload целевой TPS + пауза), что
  осознанно оставлено на усмотрение пользователя.
- **Эксплуатация.** Обычный/CI-прогон не печатает блоки; декларированной нагрузки на диск/сеть нет.

## 7. Открытые вопросы

1. **Длительность демо-прогона.** Решением владельца без параметров демо ограничено по времени:
   `--duration-sec 60` (вместо бюджета `--tx 500`). Прочие дефолты (`--nodes`, `--tx`, вне демо —
   `--concurrency`) не меняются. Осознанно: прогон без параметров длится ~1 минуту и легко обозрим;
   `Ctrl+C` по-прежнему допустим.
2. **Точный вид блока** (набор и порядок строк, символы рамки, сокращение хэшей/адресов) —
   зафиксировать при реализации по образцу в [`plan.md`](plan.md) §4; допустимы правки по вкусу.
3. **Печатать ли строку «ожидание»** во время случайной паузы (например, тонкую точку/`…`) — не
   обязательно; по умолчанию без неё, чтобы stdout оставался машинно-чистым.
