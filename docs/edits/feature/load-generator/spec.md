## 2. Проблема и сценарий

### 2.1. Формулировка владельца (дословно)

> «у меня есть такой код: … это бот для нагрузочного тестирования. сможем мы грамотно
> интегрировать его в проект? протестировать и всё такое… стоит включить его в основное
> автоматическое тестирование, думаю. кажется это удобно.»

Уточнения, полученные в наводящих вопросах:

- **язык** — переносим на Rust (переиспользуем домен/канонический хэш проекта, без Python и `keys.py`);
- **место в тестировании** — отдельно, **не** в `cargo test`; тяжёлый прогон — опциональный бинарь/скрипт
  плюс отдельная CI-задача;
- **топология** — in-process кластер (поднимаем узлы в процессе инструмента, без docker);
- **генераторы** — один настраиваемый (целевой TPS/длительность/конкурентность), без «реалистичных» надстроек;
- **логика бота** — исправляем под текущие инварианты (монотонный `seq`, корректный выбор родителей, баг `HOST[i]`);
- **результат прогона** — корректность + лог (throughput/латентность печатаются, жёсткого SLA нет);
- **объём сейчас** — только ТЗ/план, реализация отдельной сессией.

### 2.2. Проблема

В проекте есть функциональные проверки (`benches/graph_bench.rs` — граф в вакууме; `tests/api`,
`tests/cluster` — корректность на десятках транзакций), но **нет инструмента, который длительно
гоняет реальный поток подписанных транзакций через `POST /` и кластерный консенсус**, измеряя
throughput, задержку и консистентность реплик. Владелец использовал для этого внешний Python-скрипт.

Скрипт **несовместим с текущим кодом** и не может быть принят как есть:

- `seq = random.randint(...)` нарушает инвариант **V18** (`Dag.last_seq`, `AGENTS.md` §6,
  `store.rs::validate_add` → `dag.accepts_seq`): `seq` адреса обязан строго возрастать, иначе
  почти все транзакции получают прикладной отказ;
- `prnts = pool_data["nodes"]` берёт весь пул: может быть `< 2` или `> 100`, а `validate_parents`
  (2..100, только живой DAG) такие транзакции отклоняет;
- `HOST = random.choice([...])` возвращает **строку**, затем `HOST[i]` индексирует *символ* —
  `run_sender`/`send` получают мусор вместо адреса;
- дефолтный `PUBLIC_RATE_LIMIT_PER_SEC=50` превратит прогон в поток `429`;
- канонический хэш и подпись дублируются в Python (`src.utils.data.ordered_sum`, `src.utils.crypto`),
  что может разойтись с `utils.rs`.

### 2.3. User story / кейсы

1. Как **разработчик**, я хочу одной командой прогнать поток валидных транзакций через локальный
   in-process кластер и увидеть принятые/отклонённые, достигнутый TPS и перцентили задержки —
   чтобы проверять изменения горячего пути не только микро-бенчмарками.
2. Как **дежурный/релиз-инженер**, я хочу опциональную `workflow_dispatch`/nightly CI-задачу,
   которая прогоняет короткий нагрузочный сценарий и падает при нарушении корректности
   (прикладной отказ валидной транзакции или расхождение реплик), — чтобы ловить регрессии,
   не замедляя обычный PR-пайплайн.
3. Как **владелец**, я хочу, чтобы нагрузка генерировалась валидными транзакциями по тем же правилам,
   что применяет state machine (единый источник истины — код проекта), а не копией логики.

**Успех:** инструмент запускается, генерирует валидные транзакции, все принятые транзакции
консистентны на всех репликах, а отчёт печатается в stderr/JSON; реализовано отдельной сессией.

## 3. Требования

### 3.1. Функциональные (в терминах поведения/контракта)

- **R1. Рантайм-инструмент.** Отдельный бинарник (`loadgen`) + скрипт-обёртка; **не** входит в
  `cargo test --all` и не запускается по умолчанию. Реализация на Rust, переиспользует
  `dagdb::{start_raft, utils::ordered_sum, Tx, domain::*, graph::dag::TRANSFER_TOKEN}` и
  `dagdb::server::start_server`.
- **R2. In-process кластер.** Поднимает `--nodes N` узлов dagdb в одном процессе (каждый — на своём
  потоке/runtime), инициализирует кластер, добавляет learners и меняет membership, грузит
  `genesis.json` через внутренний API с токеном. Redis обязателен (как и для `tests/cluster`).
- **R3. Валидная нагрузка.** Генератор строит транзакции, проходящие детерминированную валидацию:
  - `prnts` — `k` **живых** узлов из `/pool`, `2 ≤ k ≤ min(100, |pool|)`; при `|pool| < 2` — ожидание;
  - `seq` — **строго монотонный по адресу** (каждый аккаунт ведёт свой счётчик, начиная с 1);
  - `func = transferToken`, `var` корректной структуры (`ca`/`to` непусты, `val ≥ 0`, `msg ≤ 2500`);
  - `sign` — ed25519 над `ordered_sum(tx, "transferToken")` (тот же код, что в `utils.rs`).
- **R4. Настраиваемый генератор (один).** Параметры: количество транзакций либо длительность,
  целевой TPS, конкурентность (число sender-задач), число аккаунтов, число/диапазон родителей,
  seed для воспроизводимости.
- **R5. Отчёт и корректность.** Печатает: принято/отклонено с разбивкой по причинам, достигнутый
  TPS, перцентили задержки клиента, итоговый размер DAG по каждой реплике. **Корректностные инварианты**
  (обязательные, влияют на код возврата): нет прикладных отказов у заведомо валидных транзакций;
  итоговый размер DAG одинаков на всех репликах. Throughput/латентность — **информационные** (без SLA).
- **R6. Ограничение очистки.** На время прогона фоновая очистка «тяжёлых» узлов отключается
  (`cleanup_batch_size = 0` либо `processor_interval` заведомо большой) и rate limit публичного API
  выключается (`public_rate_limit_per_sec = 0`), иначе родители «уезжают» в `added`, а часть
  запросов ловит `429` — и корректностный инвариант станет недостижимым.
- **R7. Опциональная CI-задача.** Отдельный job (не в `check`), запускаемый вручную
  (`workflow_dispatch`) и/или по расписанию (nightly): Redis-сервис, сборка release, короткий
  прогон, ненулевой код возврата при нарушении корректности.
- **R8. Документация.** Раздел в `README.md` (запуск/параметры) и запись в `docs/edits/feature/`.

### 3.2. Не-функциональные

- Детерминизм при фиксированном `--seed` (последовательность параметров транзакций воспроизводима;
  фактическая задержка Raft — нет, но распределение от неё не зависит).
- Никаких изменений канонического хэша/подписи, формата состояния/лога, `SCHEMA_VERSION`, контракта
  Raft-типов, публичного HTTP-API — инструмент использует существующий `POST /` и `/pool`.
- Инструмент не должен замедлять обычную сборку/тесты (кроме компиляции таргета под clippy).
- Секреты — только из env/CLI; в коде и docs реальных ключей/токенов нет.

## 4. Границы и не-цели

**Входит в скоуп:** перенос генератора на Rust; один настраиваемый профиль нагрузки; in-process
кластер; корректностные проверки (приём валидных tx + консистентность реплик); отчёт в лог/JSON;
скрипт-обёртка; опциональная CI-задача; документация.

**MVP (первый этап):** in-process кластер (фикс. 3–4 узла) + один генератор + корректность + лог-отчёт
+ скрипт. **Полный вариант:** настраиваемые узлы/родители/seed, JSON-отчёт, внешний режим `--target`,
CI-job, перцентили задержки.

**Не-цели (осознанно вне скоупа):**

- Не восстанавливаем «реалистичные» генераторы исходника (тренды/суточный множитель/микрокластеры) —
  решением владельца оставлен один настраиваемый профиль.
- Не заменяем `benches/graph_bench.rs` (микро-бенчмарк графа) и `tests/cluster` (корректность).
- Не добавляем нагрузочные пороги как обязательный шаг PR-CI.
- Не трогаем Python-скрипт владельца и его зависимости (`keys.py`, `httpx`).
- Не реализуем TLS/распределённую генерацию нагрузки (несколько машин) и не измеряем ресурсы узлов
  (CPU/RSS) — при необходимости отдельной задачей.
- Не меняем публичный API/схему состояния.

## 5. Влияние

- **Инварианты (`AGENTS.md` §6).** Инструмент **использует** инварианты, не меняет их: канонический
  хэш/подпись — вызов `ordered_sum`; монотонный `seq` — соблюдается генератором; уникальность хэша —
  обеспечивается монотонным `seq`/уникальным содержимым; разделение API — генератор ходит во внутренние
  ручки только с `x-internal-token`; Raft-контракт не трогается.
- **Совместимость.** Аддитивно: новых полей состояния, команд и версий схемы нет, `SCHEMA_VERSION` не
  поднимается. Публичный HTTP-контракт без изменений → `docs/api/openapi.json` не меняется.
- **Зависимости.** Предпочтительно **без новых crate**: для ГПСЧ — маленький детерминированный
  inline-PRNG (напр. xorshift/PCG) с `--seed`, чтобы не трогать `Cargo.toml`. `clap`, `reqwest`,
  `serde_json`, `tokio`, `ed25519-dalek`, `base58`, `hex` уже есть.
- **Производительность.** Не влияет на рантайм узла; при in-process запуске нагрузочный процесс и узлы
  делят машину — это осознанное ограничение (инструмент для dev/CI, не для эталонных цифр).
- **Безопасность.** In-process режим изолирован; `--target` (если появится) должен предупреждать о
  недоверенных средах. Секреты — из env/CLI.

## 6. Связи

- **V18/C45** (`docs/edits/audit/second-pass/02-important.md`) — монотонный `seq`; генератор обязан его
  соблюдать (главная причина несовместимости исходного бота).
- **K1/C34** — прикладной отказ SM доходит до клиента `4xx`; инструмент полагается на это, чтобы
  отличать «валидную транзакцию отклонили ошибочно» от штатного дубля.
- **V15/C38** — родители только из живого DAG ⇒ источник родителей — `/pool`, а не `added`.
- **Q2/C41** (`/pool`, `/full` не держат лок) — важно для параллельной генерации.
- **O9** (`benches/graph_bench.rs`) — дополняет, не заменяет.
- **F1/F2** (`docs/edits/fix/redis-startup-hang`, `http-port-ignored`) — учтены при старте in-process узлов.
- Конфликтов с ранее реализованными фичами нет (в `docs/edits/feature/` пока пусто).
