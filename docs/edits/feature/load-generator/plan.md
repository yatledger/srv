# N01 — план реализации нагрузочного генератора (loadgen)

> Группа: **edits/feature/load-generator** · Тип: **feature** · Статус: ✅ **реализовано** (2026-10-09).
> Сопутствующие документы: [`spec.md`](spec.md) (ТЗ), [`tracker.md`](tracker.md), [`report.md`](report.md).
> Регламент: [`AGENTS.md`](../../../../AGENTS.md) · формат фич: [`../README.md`](../README.md).
> Коммит-база: `0c5cf44`. Реализация выполнена отдельной сессией (см. `report.md`).

## 1. Цель и границы

Перенести внешний Python-бот нагрузочного тестирования в проект на Rust как отдельный
рантайм-инструмент `loadgen`, который поднимает in-process кластер `dagdb`, гонит валидный поток
подписанных транзакций через `POST /`, проверяет корректность (приём валидных tx + консистентность
реплик) и печатает отчёт. Инструмент вне `cargo test`; тяжёлая проверка — отдельная CI-задача.

Границы и не-цели — см. [`spec.md`](spec.md) §4.

## 2. Требования к поведению после реализации

См. R1–R8 в [`spec.md`](spec.md) §3. Кратко: in-process кластер; валидные транзакции (монотонный
`seq`, 2..100 живых родителей, корректный `var`, подпись через `ordered_sum`); один настраиваемый
генератор; отчёт с корректностными инвариантами и информационными throughput/перцентилями; очистка и
rate limit выключены; опциональная CI-задача; документация.

## 4. Шаги реализации

Порядок — по этапам с независимой проверкой. Один коммит = один логически завершённый шаг
(Conventional Commits, `Refs: N01`).

### Этап 1 — каркас и in-process кластер

1. Добавить `src/bin/loadgen.rs` с подмодулями и clap-парсером параметров
   (`--nodes`, `--tx`|`--duration-sec`, `--tps`, `--concurrency`, `--accounts`, `--parents`,
   `--seed`, `--json-out`, `--keep-data`, `--verbose`).
2. `cluster.rs`: поднять `N` узлов через `start_raft` + `server::start_server`; каждый узел — на своём
   `std::thread` c current-thread runtime (чтобы нагрузочный драйвер и узлы не воевали за воркеры);
   свободные порты, временные `DATA_DIR`, общий `INTERNAL_API_TOKEN`;
   `AppConfig`: `public_rate_limit_per_sec = 0`, `cleanup_batch_size = 0`, `Profile::Dev`.
3. Bootstrap: ожидание `/health`; `POST /mng/init`; ожидание лидера через `/mng/metrics`;
   `POST /mng/add-learner` и `/mng/change-membership`; `POST /load-genesis` (`genesis.json`
   читается из корня крейта через `env!("CARGO_MANIFEST_DIR")`).
4. Завершение: `app.shutdown.trigger()`, `raft.shutdown()`, join потоков; очистка временных каталогов.

### Этап 2 — генератор валидных транзакций

5. `prng.rs`: детерминированный ГПСЧ (xorshift/PCG) + `--seed`; равномерные `u64`/диапазоны.
6. `generator.rs`:
   - аккаунты: `--accounts` ключей ed25519 (`SigningKey::from_bytes` из seed-производных байт),
     адрес — `verifying_key().to_bytes().to_base58()`;
   - на каждый аккаунт — **свой атомарный счётчик `seq`** (начинается с 1, строго возрастает);
     sender берёт аккаунт по round-robin/пулу, чтобы не сериализовать счётчик;
   - родители: `GET /pool`, взять `k = clamp(--parents, 2, min(100, |pool|))` живых узлов
     (пул уже отсортирован по числу родителей — сохраняем логику «наименее связанных»);
     при `|pool| < 2` — короткий ретрай/ожидание;
   - `var`: `{ ca: <addr отправителя>, to: <случайный адрес>, val: <u64>, msg: <строка ≤2500> }`;
   - `hash = ordered_sum(&tx, TRANSFER_TOKEN)`, `sign = hex(sk.sign(hash.as_bytes()))`.

### Этап 3 — драйвер и отчёт

7. `runner.rs`: `--concurrency` sender-задач; регулирование целевого TPS токен-бакетом/интервалом
   (один общий планировщик или per-worker target = tps/concurrency); сбор `(status, reason, latency)`.
8. `report.rs`: подсчёт принятых/отклонённых с разбивкой по причинам (`Rejected` из K1 приходит
   текстом), достигнутого TPS, перцентилей задержки (p50/p95/p99), итоговых размеров DAG по репликам.
   **Корректностные проверки, влияющие на код возврата:**
   - нет прикладных отказов у валидных транзакций (кроме явно ожидаемых — например, осознанно
     тестируемых дублей, но по умолчанию их нет);
   - `GET /full` на всех узлах даёт одинаковый `total`.
   Информационные метрики (TPS/перцентили) не влияют на код возврата.
9. `--json-out` — машинно-читаемый отчёт для CI-артефакта (схема фиксируется в этом плане:
   `{ params, accepted, rejected: [{reason,count}], achieved_tps, latency_ms:{p50,p95,p99},
   dag_total_per_node: {node_id: total}, ok, errors: [] }`).

### Этап 4 — скрипт, CI, документация

10. `scripts/loadgen.sh`: проверить Redis (быстрый ping), собрать release, запустить `loadgen` с
    дефолтами (короткий прогон), прокинуть остальные аргументы.
11. `.github/workflows/ci.yml`: job `load` (Redis-сервис, `cargo build --release`, короткий прогон,
    публикация JSON-отчёта артефактом). Триггеры — `workflow_dispatch` (+ при желании `schedule`
    nightly), **не** в `pull_request`. Существующий job `check` не меняем.
12. `README.md`: раздел «Нагрузочное тестирование» (что делает, как запустить, параметры, ограничения
    in-process). Обновить `docs/edits/feature/README.md`.

## 5. Тесты

- **Юнит-тесты инструмента** (`#[cfg(test)]` в `generator.rs`/`report.rs`/`prng.rs`):
  - монотонность `seq` при параллельной выдаче аккаунта;
  - выбор `k` родителей в границах `2..=min(100,|pool|)`;
  - детерминизм ГПСЧ при одном `--seed`;
  - агрегация отчёта и правило «OK/ошибка».
- **Не добавляем** обязательных нагрузочных тестов в `cargo test --all` (решение владельца): тяжёлый
  путь живёт в `loadgen` + отдельной CI-задаче. Существующие `tests/api`/`tests/cluster` остаются как есть.
- `cargo fmt --all`, `cargo clippy --all-targets -- -D warnings` должны покрывать новый таргет;
  `cargo test --all` — зелёный (Redis для интеграционных).

## 7. DoD

- `loadgen` запускается на локальной машине с Redis и завершает короткий прогон с кодом `0`;
- печатает принятые/отклонённые (по причинам), достигнутый TPS, p50/p95/p99, размер DAG по репликам;
- при детерминированном `--seed` параметры транзакций воспроизводимы;
- все валидные транзакции приняты и DAG консистентен на всех репликах;
- `cargo fmt --all`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all` — зелёные
  (Redis для интеграционных; при отсутствии — явно сообщено);
- инварианты `AGENTS.md` §6 не нарушены; `SCHEMA_VERSION`/Raft-контракт/публичный API не менялись;
- добававлена опциональная CI-задача, не удлиняющая PR-пайплайн; `README.md` и `docs/edits/feature/`
  обновлены.

## 8. Риски и откат

| Риск | Митигация |
|---|---|
| In-process узлы и драйвер делят CPU → заниженный TPS | это инструмент корректности, не эталонных цифр; узлы на своих потоках; цифры помечены информационными |
| Флейки из-за выбора родителей, «уехавших» в `added` | очистка выключена (`cleanup_batch_size=0`); ретрай при `|pool|<2`; тесты на границы |
| `429` из-за rate limit | rate limit выключен в конфиге инструмента |
| Недетерминизм Raft (таймауты выборов) | bootstrap с ожиданием лидера/готовности; ретраи; `seq`/содержимое детерминированы, задержка — нет |
| Новый таргет ломает clippy/сборку | компиляция под `clippy --all-targets`; при необходимости `[[bin]]` с явным описанием |
| Долгий/тяжёлый CI | job вне PR; короткий сценарий; manual/nightly |
| Расхождение с каноническим хэшем | используем `dagdb::utils::ordered_sum`, копий логики нет |

**Откат:** изменения аддитивны (новые файлы + отдельный CI-job + раздел README). Удаление новых файлов
и job возвращает проект в исходное состояние; данные/схема не затрагиваются, миграция не нужна.
Точка отката — коммит-база `0c5cf44`.

## 9. Этапность и вне скоупа

- **Этап 1 (MVP):** in-process кластер + генератор + базовый лог-отчёт + скрипт.
- **Этап 2:** JSON-отчёт, перцентили, настраиваемые родители/аккаунты, `--seed`.
- **Этап 3:** CI-job, документация.
- **Вне скоупа:** «реалистичные» генераторы, распределённая нагрузка, пороги SLA в PR-CI, внешний
  `--target` (кандидат в отдельную задачу), измерения ресурсов узлов.
