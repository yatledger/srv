## 2. Симптом и ожидание

**Воспроизведение.**

```bash
docker run -d --name dagdb-redis-test -p 6380:6379 redis:7-alpine
REDIS_URL=redis://127.0.0.1:6380/0 cargo test --test cluster
```

**Наблюдаемое** (паника, `tests/cluster/test_cluster.rs:394`):

```
thread '…cluster_init_membership_replication_snapshot_restart_concurrent' panicked at tests/cluster/test_cluster.rs:394:9:
конкурентная запись отклонена: 400 Bad Request
```

Тело ответа (получено временным диагностическим патчем, затем откат):

```json
{"status":"error","message":"non-monotonic seq for <addr base58>: got 104, last applied 108"}
```

Сбой **детерминированный** — 6 прогонов из 6 упали. Это не флейк тайминга, а
закономерная инверсия порядка применения.

**Ожидаемое.** Кластерный тест «конкурентные записи» должен проходить: либо все 10
транзакций принимаются (если тест переписан под реальный контракт), либо тест
должен быть приведён в соответствие с детерминированной проверкой монотонности
`seq` (V18) и задокументированный контракт соблюдён.

## 3. Анализ причины

Цепочка вызовов (по текущему дереву):

1. `tests/cluster/test_cluster.rs:383-391` — шаг 7 «конкурентные записи»: 10 задач
   `tokio::spawn` **одновременно** шлют `POST /` в **лидера напрямую** (`node1`).
2. `tests/cluster/test_cluster.rs:384,387` — тело собирается
   `signed_tx(&sk, &addr, &[p1,p2], 100 + seq)`, `seq = 100..=109`, при этом
   **адрес `addr` и ключ `sk` одни и те же** для всех 10 задач (`keypair(7)`,
   строка 349).
3. `src/server.rs:146` (`add_tx`) → `src/server.rs:123-135`
   (`validate_and_prepare_tx`): ранняя проверка структуры и состояния. Проверки
   **монотонности `seq` здесь нет** (это политика state machine, а не входного API).
4. Все 10 запросов доходят до лидера и вызывают `app.raft.client_write(request)`
   (`src/server.rs:276`) **параллельно**.
5. openraft добавляет записи в лог в порядке фактического прибытия/обработки, а не
   в порядке `spawn`. Порядок применения на репликах — порядок лога.
6. `src/raft/store.rs:333` (`apply`) → `validate_add` → `src/raft/store.rs:60`:
   `dag.accepts_seq(&tx.addr, tx.seq)?`.
7. `src/graph/dag.rs:162-172` (`accepts_seq`): для одного `addr` требует строго
   `seq > last_seq`; `last_seq` обновляется на максимум при каждом add
   (`src/graph/dag.rs:147-154`).

**Корневая причина.** Тест шлёт **разные `seq` одного адреса конкурентно**, не
сериализуя их. При таком паттерне порядок применения не обязан совпадать с
порядком `seq`, поэтому рано или поздно транзакция с меньшим `seq` применяется
после транзакции с большим — и детерминированная анти-replay защита (V18/C45)
корректно отклоняет её. `400` — ожидаемое поведение state machine; дефект — в
**тесте**, который противоречит задокументированному контракту
`docs/api/API.md:77` («`seq` адреса обязан строго возрастать»).

Проверка причины: ответ `got 104, last applied 108` показывает, что 108 применился
раньше 104. Это ровно та инверсия, которую ловит `accepts_seq`.

**Регрессия?** Да, ⚠️. Блокировка «конкурентные записи» и тела с `100 + seq`
добавлены в `9c78640` (**O1**) ещё **до** V18; тест с тех пор не менялся. Проверка
монотонности `seq` и `last_seq` добавлены позже, в `6f75117` (**V18/C45**),
который не согласовал старый тест. Почему V18 отчитался «зелёным» — см. §5.

## 4. Влияние

- **CI/регрессия.** `cargo test --all` не проходит; единственный кластерный тест
  (инициализация, membership, репликация, снапшот, рестарт, конкурентные записи)
  не выполняется до конца. Прочие наборы (`lib`, `api`) зелёные.
- **Прод.** Не затронут. `accepts_seq` корректна и соответствует контракту
  `docs/api/API.md:77` и решению владельца по C45/V18 (анти-replay). Изменять
  поведение state machine в этой задаче **не требуется**.
- **Инварианты (`AGENTS.md` §6).** Детерминизм state machine не нарушается — как
  раз наоборот. Канонический хэш/подпись, `added`, контракт Raft-типов,
  `SCHEMA_VERSION` — не задеты и не должны меняться.
- **Другие места.** Тот же паттерн (несколько `seq` одного адреса параллельно без
  сериализации) в `src/bin/loadgen/generator.rs` **отсутствует**: генератор
  намеренно удерживает `account_gate` до ответа (строки 39-41, 86-93, 97-98) —
  это корректный способ клиента. Других тестов с этим дефектом нет.

## 5. Связи

- `V18` / `C45` (`docs/edits/second-pass/tracker.md:32,84`,
  `docs/edits/audit/second-pass/audit.md:108`) — внесли проверку монотонности
  `seq`, породившую регрессию.
- `O1` (`9c78640`) — внёс блок конкурентных записей и тела `100 + seq`.
- `F1` (`docs/edits/fix/redis-startup-hang/`) — зафиксировала сбой как
  предсуществующий (см. `report.md`, «Предсуществующий сбой кластерного теста»);
  эта задача — тот самый отдельный разбор.
- **Почему V18 был заявлен зелёным.** В трекере second-pass (`tracker.md:84`)
  прогон `test --all` показал «1 cluster», но рядом (`tracker.md:81`) отмечено,
  что Redis был недоступен и интеграционные **пропускались**. Кластерный тест при
  недоступном Redis сам себя пропускает (`tests/cluster/test_cluster.rs:288-291`,
  вывод `SKIP` считается успехом) — поэтому реальный сценарий не выполнялся, и
  регрессия не была замечена.
- **Дублирование?** Нет. `accepts_seq` покрыта юнит-тестами
  (`src/raft/store.rs:610-643`, `src/graph/dag.rs:770-795`); ломается только
  сценарий интеграционного теста.

## 6. Открытые вопросы владельцу

1. **Где чинить.** Считать дефект **тестовым** (правим сценарий
   `tests/cluster/test_cluster.rs`) и не трогать state machine? Рекомендуется: да.
   Альтернатива — менять семантику анти-replay (напр. окно допуска/буфер по
   адресу), но это ломает решение владельца по C45 и детерминизм, поэтому не
   рекомендуется.
2. **Как сохранить смысл теста.** Оставить «конкурентность» за счёт **разных
   адресов** (каждая задача — свой ключ и `seq`, общий лидер) — рекомендуемый
   вариант: проверяет параллельные `client_write` без нарушения per-address
   порядка. Или сделать отправку **последовательной** в рамках одного адреса
   (минимальная правка, но теряется конкурентность)?
3. **Ассерт по количеству узлов.** После фикса шаг проверки
   `wait_node_count(..., 14)` (3 генезис + 1 промежуточная + 10 конкурентных)
   остаётся валидным при любом из вариантов (все 10 принимаются).
4. **Документация.** Нужно ли дополнительно подчеркнуть в `docs/api/API.md`/
   `README.md`, что при конкурентной отправке одного адреса клиент **обязан**
   сериализовать `seq` (сейчас сказано лишь «строго возрастать»)?
5. **Приоритет.** Тянуть сейчас (CI красный) или зафиксировать план? Не влияет на
   прод-поведение, но блокирует зелёный `cargo test --all`.
