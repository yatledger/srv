# План устранения: конкурентная запись в кластерном тесте vs монотонность `seq` (F3)

> Группа: **edits/fix/cluster-concurrent-seq** · Тип: **fix** · Статус: **план согласован (вариант A), готов к реализации**.
> Решение владельца (2026-10-09): шаг 7 — **разные адреса** (конкурентность сохраняется), объём —
> **тест + уточнение docs**, приоритет **P2**.
> Ссылки: [`defect.md`](defect.md) (паспорт дефекта), [`tracker.md`](tracker.md), [`report.md`](report.md).

## 1. Цель и границы

**Чиним.** Кластерный тест
`cluster_init_membership_replication_snapshot_restart_concurrent`
(`tests/cluster/test_cluster.rs`) должен проходить на текущем коде, не нарушая
задокументированный контракт монотонности `seq` (`docs/api/API.md:77`, V18/C45).

**В скоупе:**
- `tests/cluster/test_cluster.rs` — привести шаг 7 «конкурентные записи» в
  соответствие с контрактом `seq`: конкурентные записи идут от **разных** адресов
  (выбранный владельцем вариант A).
- `docs/api/API.md` / `README.md` — уточнить, что клиент обязан сериализовать `seq`
  одного адреса, а при конкурентной отправке использовать разные аккаунты.

**Вне скоупа (осознанно):**
- Изменение state machine / `accepts_seq` / семантики анти-replay (V18/C45). Она
  корректна и соответствует решению владельца; трогать не следует.
- Любые изменения формата состояния, `SCHEMA_VERSION`, канонического хэша/подписи,
  Raft-контракта, публичного/внутреннего API.

## 2. Требования к поведению после фикса

1. `tests/cluster/test_cluster.rs::…concurrent` проходит с Redis.
2. Тест по-прежнему проверяет **конкурентную** отправку `POST /` в лидера
   (несколько одновременных `client_write`), а не превращается в
   последовательный цикл.
3. Все отправленные транзакции принимаются (`200`), итоговое число узлов
   `wait_node_count(..., 14)` достигается (3 генезис + 1 промежуточная + 10
   конкурентных).
4. Контракт монотонности `seq` соблюдён: ни одна пара конкурентных транзакций не
   принадлежит одному адресу с конфликтующим `seq`.
5. `cargo test --all` зелёный (Redis для интеграционных).

## 4. Шаги реализации (порядок)

1. **Решение владельца** по варианту теста (§8) — зафиксировать в `plan.md`/`tracker.md`.
2. **Тест (вариант A).** Переписать шаг 7:
   - в цикле `for i in 0..10u8` строить `let (addr, sk) = keypair(20 + i);` и
     `let body = signed_tx(&sk, &addr, &[p1.clone(), p2.clone()], 0);`
   - каждая задача шлёт свою транзакцию (уникальный адрес, независимый `last_seq`)
     в лидера параллельно;
   - обновить комментарии у блока: объяснить, что `seq` одного адреса нельзя
     параллелить (иначе `non-monotonic seq`, V18), поэтому конкурентность
     обеспечивается разными аккаунтами.
3. **Docs.** Уточнить формулировку про `seq` в `docs/api/API.md` и `README.md`:
   `seq` монотонен **в рамках адреса**; при конкурентной отправке использовать
   разные адреса; один адрес клиент сериализует.
4. **Проверки.** `cargo fmt --all`, `cargo clippy --all-targets -- -D warnings`,
   `cargo test --all` (Redis), `cargo bench --no-run`.
5. **Ручное подтверждение.** `REDIS_URL=… cargo test --test cluster` — зелёный;
   повторный прогон подтверждает отсутствие прежнего `non-monotonic seq`.

## 5. Тесты

- **Регрессионный (обязателен).** Сам кластерный тест: **до фикса** падает на
  шаге 7 с `400`/`non-monotonic seq` (воспроизведено 6/6), **после фикса**
  проходит. Требует Redis.
- **(Опционально) Детерминированный юнит-тест** в `src/raft/store.rs` или
  `src/graph/dag.rs`: применение двух `Add` одного адреса с `seq` в обратном
  порядке отклоняется, а в прямом — принимается. Отчасти уже покрыто
  `add_rejects_non_monotonic_seq_for_same_addr` и roundtrip-тестом `last_seq`;
  добавлять только если хотим явно зафиксировать сценарий инверсии порядка лога.
- Существующие наборы (`lib`, `api`) ломать нельзя.

## 7. Риски и откат

| Риск | Митигация |
|---|---|
| Вариант A меняет смысл теста (больше не проверяет один «перегруженный» аккаунт) | Осознанно (решение владельца): контракт запрещает параллельный `seq` одного адреса. Конкурентность `client_write` сохраняется. |
| Разные ключи создают лишние адреса и влияют на `last_seq` | `last_seq` — по адресу; каждый новый адрес независим, коллизий нет. |
| Тест требует Redis и в среде без него «пропускается» (SKIP) | Явно предупреждать в отчёте; прогонять с поднятым Redis (`docker run … -p 6380:6379 redis:7-alpine`). |

Миграции состояния/`SCHEMA_VERSION` не требуются.
