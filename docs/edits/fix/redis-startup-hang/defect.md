## 2. Симптом и ожидание

Дословная формулировка владельца:

> `NODE_ID=1 HTTP_PORT=21001 DATA_DIR=./data/node1 ./target/release/dagdb`
> `curl http://127.0.0.1:21001/` → `curl: (7) Failed to connect to 127.0.0.1 port 21001 after 0 ms: Connection refused`

Шаги воспроизведения:

1. Остановить Redis (`docker stop dagdb-redis`) либо задать неверный `REDIS_URL` (несовпадающий пароль).
2. Запустить узел: `NODE_ID=1 HTTP_PORT=21001 DATA_DIR=./data/node1 ./target/release/dagdb`.
3. Наблюдать: процесс жив, но `ss -tln` не показывает порт `21001`; `curl`/`GET /` → connection refused.
4. Артефакт-следствие: повторный запуск в том же `DATA_DIR` падает с
   `Error: "Database already open. Cannot acquire lock."`, потому что первый (зависший) процесс
   продолжает держать блокировки redb (`data/node1/raft-log.redb`, `data/node1/state-machine.redb`).

**Наблюдаемое.** `start_raft` навсегда блокируется на подключении к Redis, HTTP-сервер
(`TcpListener::bind`) не запускается. Процесс выглядит «живым» (тикает Raft-ядро), но не отвечает.

**Ожидаемое.** Если Redis недоступен или аутентификация не проходит, узел должен **быстро и
предсказуемо** завершиться с понятным сообщением об ошибке (без бесконечного зависания и без
удержания блокировок redb), вместо невнятного «connection refused» на следующем шаге.

## 3. Анализ причины

Цепочка вызовов:

1. `src/main.rs:34` — `AppConfig::load()`; `src/main.rs:49` — `start_raft(&cfg).await?`.
2. `src/lib.rs:108` — `start_raft`: сначала собираются redb-хранилища и запускается Raft
   (`src/lib.rs:131-150`), затем подключается Redis.
3. `src/lib.rs:159-161` — **корневое место**:
   ```rust
   let redis_url = cfg.redis_url()?;
   let redis_client = redis::Client::open(redis_url)?;
   let redis = ConnectionManager::new(redis_client).await?;   // нет таймаута
   ```
   `ConnectionManager::new` не обёрнут в `tokio::time::timeout` и не имеет собственного лимита
   времени на уровне приложения.
4. `src/lib.rs:163-182` — `App::new(...)`; `src/server.rs:937` — `TcpListener::bind(&bind_addr)`
   выполняется **только после** возврата из `start_raft`. Пока Redis-подключение не завершится,
   порт не открывается → `curl` получает connection refused.
5. `src/lib.rs:143-150` — `openraft::Raft::new(...)` стартует фоновое Raft-ядро **до** подключения к
   Redis, поэтому процесс не выглядит «мёртвым»: он тикает и держит redb-лocks, маскируя зависание.

**Почему нет ошибки.** Внутри `redis` 0.32.0 `ConnectionManager::new`
(`src/aio/connection_manager.rs`) использует `ExponentialBuilder` (`factor=100`, 6 попыток) и
pipeline аутентификации (`setup_connection` → `execute_connection_pipeline`). В проверенном сценарии
этот путь **не завершается ошибкой**, а зависает:

- Минимальный репро на `redis = "=0.32.0"` (вне репозитория, `/tmp/opencode/redistest`), 30-секундный
  `tokio::time::timeout` вокруг `ConnectionManager::new`:
  - Redis не слушает порт → `HUNG (timeout after 30s)`;
  - Redis слушает, но без пароля, клиент шлёт пароль (`-ERR AUTH <password>`) → `HUNG (timeout after 30s)`;
  - Redis с корректным `--requirepass` и верным паролем → `connected OK`.
- В приложении зависание **неограниченно**: эксперименты с `timeout 100s` и `240s` — процесс жив,
  HTTP не поднят; в gdb главный поток стоит в `park` (ожидание), сетевой прогресс не идёт.

**Корневая причина (формулировка).** Отсутствие ограничения времени на `ConnectionManager::new` в
`src/lib.rs:161` в сочетании с тем, что клиент `redis` 0.32 не сообщает об ошибке подключения/аутентификации
в этих сценариях: узел блокируется на старте до HTTP-bind, превращая недоступный/неверно
сконфигурированный Redis в немой «отказ в соединении».

**Дополнительный фактор (docs/config).** Инструкция локального запуска в `README.md:135`
поднимает Redis **без пароля** (`docker run … redis:7-alpine`), тогда как `.env`/`.env.example:24`
задают URL **с паролем** (`redis://:…@localhost:6379/0`). `docker-compose.yml` же передаёт
`--requirepass ${REDIS_PASSWORD}`, то есть настроен согласованно. Свежий пользователь, идущий по
README, гарантированно попадает в сценарий несовпадения пароля → зависание.

## 4. Влияние

- **Доступность узла (🟠).** Любой простой Redis или ошибка в `REDIS_URL` полностью блокирует старт
  без диагностики; пользователь видит лишь «connection refused».
- **Побочный эффект.** Зависший процесс удерживает redb-блокировки, из-за чего повторный запуск
  падает с `Database already open` — симптом множится и путает диагностику (наблюдалось у владельца).
- **Детерминизм/целостность.** Не затронуты: канонический хэш/подпись, `added`/уникальность,
  контракт Raft-типов, `SCHEMA_VERSION` не меняются. Правка касается только инициализации
  подключения к Redis.
- **Эксплуатация.** `/ready` и очистка/архивация требуют Redis; при недоступном Redis узел и так
  нефункционален, поэтому «не подниматься молча» — худший из вариантов (предпочтительнее явный отказ).

## 5. Связи

- Аудиты `big-bang`/`second-pass`: отдельной находки про зависание старта на Redis нет —
  **не дубль**. Близкая тема: решение владельца «Redis — окончательная зависимость»
  (`docs/edits/audit/second-pass/tracker.md:82`) и то, что интеграционные тесты уже оборачивают
  `ConnectionManager::new` в `tokio::time::timeout` (`tests/api/test_api.rs:112`,
  `tests/cluster/test_cluster.rs:268`) — приложение этого не делает.
- Регрессия? Нет. Строка `ConnectionManager::new(...).await?` появилась в `3c59c6d`
  (`security(config): load all configuration and secrets from environment`) — это не смена
  поведения, а перенос секрета в env; неограниченность подключения существует с тех пор.

## 6. Открытые вопросы владельцу

1. **Семантика старта.** Предпочтительно **fail-fast**: ограниченный таймаут + явная ошибка и
   завершение процесса (Redis — окончательная зависимость). Альтернатива — поднимать HTTP сразу, а
   Redis подключать лениво/в фоне, `/ready` репортит `not_ready` (крупнее по изменениям). См. `plan.md`.
2. **Таймаут.** Ввести `REDIS_CONNECT_TIMEOUT_SECS` (рекомендуется) или переиспользовать один из
   существующих (`HTTP_CONNECT_TIMEOUT_SECS`/`RAFT_CONNECT_TIMEOUT_SECS`)?
3. **Docs/config.** Согласовать локальный запуск Redis с паролем (рекомендуется) или, наоборот,
   убрать пароль из `.env.example`? Сейчас README и `.env.example` противоречат друг другу.
