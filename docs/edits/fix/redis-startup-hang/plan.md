# План устранения: fail-fast старта при недоступном Redis (F1)

> Группа: **edits/fix/redis-startup-hang** · Тип: **fix** · Статус: **реализован, проверки пройдены
> (см. [`report.md`](report.md))**.
> Решения владельца (2026-10-09): **fail-fast** + **новый `REDIS_CONNECT_TIMEOUT_SECS`** +
> **README: Redis с `--requirepass`**.
> Ссылки: [`defect.md`](defect.md) (паспорт дефекта), [`tracker.md`](tracker.md), [`report.md`](report.md).
> Исходный код на этом шаге **не меняется** — реализация после согласования.

## 1. Цель и границы

**Чиним.** Старт узла не должен зависать из-за Redis: подключение к Redis ограничивается по времени,
при неудаче — понятная ошибка в лог и завершение процесса, вместо блокировки до HTTP-bind и удержания
redb-блокировок.

**В скоупе:**
- `src/lib.rs` — ограничить `ConnectionManager::new` таймаутом; при ошибке вернуть
  переданную вверх типизированную/понятную ошибку.
- `src/config.rs` — новый параметр `REDIS_CONNECT_TIMEOUT_SECS` (+ `--redis-connect-timeout-secs`)
  с дефолтом и валидацией.
- Документация `.env.example`/`README.md` — синхронизировать запуск Redis с требованиями профиля
  (пароль), описать новый параметр.

**Вне скоупа (осознанно):**
- Ленивое/фоновое переподключение к Redis, при котором узел поднимает HTTP без Redis, а `/ready`
  отдаёт `not_ready`. Это альтернативная, более крупная модель (см. `defect.md` §6, вопрос 1);
  предлагается как отдельная задача `feature`.
- Замена/понижение клиента `redis` и правка его внутреннего retry-поведения.
- Любые изменения state machine, Raft-контракта, канонического хэша/подписи, `SCHEMA_VERSION`.

> **Важно:** «обернуть в `timeout`» обязательно должно жить на уровне приложения (`src/lib.rs`), а не
> полагаться на внутренние лимиты `redis` 0.32 — именно они в проверенном сценарии не срабатывают.
> Это подтверждено минимальным репро: `ConnectionManager::new` не возвращает ошибку ни при down-Redis,
> ни при неверном пароле; внешний `tokio::time::timeout` срабатывает корректно.

## 2. Требования к поведению после фикса

1. **Fail-fast.** Redis недоступен/неверный пароль → в пределах `REDIS_CONNECT_TIMEOUT_SECS` процесс
   завершается с `Err` и логом вида `Redis connection failed (...): <причина>`; HTTP не поднимается,
   redb-блокировки освобождаются (процесс завершён).
2. **Согласованные дефолты.** Параметр имеет разумный дефолт (кандидат: `5` секунд) и документирован;
   значение `> 0`.
3. **Не ломать happy-path.** При рабочем Redis узел стартует как прежде (проверённый сценарий:
   Redis с `--requirepass` + верный `REDIS_URL` → `Server running at …` и `GET /health`).
4. **Понятная диагностика.** Ошибка называет причину (недоступен/аутентификация/иное) и указывает,
   куда смотреть (`REDIS_URL`), без утечки секрета в лог.
5. **Инварианты не задеты.** Никаких изменений формата состояния/лога, публичного/внутреннего API,
   хэша/подписи.

## 3. Затрагиваемые файлы

| Файл | Роль в правке |

## 4. Шаги реализации (порядок)

1. **Конфиг.** В `src/config.rs` добавить `redis_connect_timeout_secs` (env `REDIS_CONNECT_TIMEOUT_SECS`,
   CLI `--redis-connect-timeout-secs`, дефолт `5`), геттер, валидацию `> 0`, тест дефолта/валидации.
2. **Старт.** В `src/lib.rs` заменить прямую инициализацию Redis на ограниченную:
   ```rust
   let redis_url = cfg.redis_url()?;
   let redis_client = redis::Client::open(redis_url)?;
   let redis = tokio::time::timeout(cfg.redis_connect_timeout(), ConnectionManager::new(redis_client))
       .await
       .map_err(|_| /* понятная ошибка: таймаут подключения к Redis */)?
       .map_err(|e| /* понятная ошибка: не удалось подключиться к Redis: {e} */)?;
   ```
   Ошибку сформировать без секрета. Проверить, что `start_raft` возвращает `Box<dyn Error>` — обернуть
   через `std::io::Error`/кастомный тип или `format!`-ошибку, совместимую с сигнатурой.
3. **Порядок инициализации (рекомендуется).** Подключить Redis **до** `openraft::Raft::new`, чтобы
   при недоступном Redis не оставалось запущенного Raft-ядра и открытых хранилищ. Учесть, что после
   переноса `open(path)` для redb всё ещё может кратко удерживать файлы — при завершении процесса это
   не проблема.
4. **Docs.** Обновить `.env.example` и `README.md` (новый параметр + согласованный запуск Redis).
5. **Тесты.** См. §5.
6. **Проверки.** `cargo fmt --all`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all`
   (при доступном Redis); `cargo bench --no-run`.

## 5. Тесты

- **Модульные (`src/config.rs`):** дефолт `redis_connect_timeout()`, валидация `0 → ошибка`.
- **Регрессионный (обязателен) — уровень `start_raft`.** Юнит/интеграционный тест, что
  `start_raft` при заведомо «висящем» Redis **возвращает ошибку в пределах таймаута**, а не висит.
  Вариант без внешнего Redis: использовать неработающий/недостижимый адрес (`redis://127.0.0.1:1/0`)
  с очень малым `REDIS_CONNECT_TIMEOUT_SECS` и проверить `tokio::time::timeout` вокруг `start_raft`.
  Тест должен **падать до фикса** (зависание/таймаут теста) и **проходить после**.
  Разместить в `src/lib.rs` (`#[cfg(test)]`) или отдельным интеграционным тестом.
- **Интеграционные:** существующий `tests/api`/`tests/cluster` не ломать; при отсутствии Redis они
  пропускаются — сохранить поведение.

## 7. Риски и откат

| Риск | Митигация |
|---|---|
| Слишком маленький дефолт таймаута «зарежет» медленный старт Redis в compose | Дефолт `5s`, параметр настраиваемый; в compose Redis поднимается раньше узлов (`depends_on`). |
| Перенос Redis-подключения до `Raft::new` изменит порядок открытия redb | Небольшой точечный рефактор, покрыть happy-path ручной проверкой; при сомнении — оставить порядок и только добавить timeout. |
| Двойной таймаут (внутренний retry `redis` + внешний) даст ложные срабатывания | Внешний timeout заведомо больше, чем время успешного рукопожатия; happy-path проверен. |
| Ошибка в логе раскроет секрет | Формировать сообщение без `REDIS_URL` с паролем. |

**Откат.** Правка локальна (`config.rs`, `lib.rs`, docs); откат — `git revert` соответствующего
коммита. Миграции состояния/`SCHEMA_VERSION` не требуются, поэтому откат безопасен.

## 8. Открытые вопросы / решения владельца

Решено владельцем 2026-10-09:
1. **Семантика старта** — **fail-fast** (таймаут + выход с ошибкой). Ленивый старт — вне скоупа.
2. **Источник таймаута** — **новый `REDIS_CONNECT_TIMEOUT_SECS`** (дефолт `5`), не переиспользуем
   существующие `HTTP_/RAFT_CONNECT_TIMEOUT_SECS`.
3. **Docs** — привести `README.md` к запуску Redis с `--requirepass $REDIS_PASSWORD` и согласовать с
   `.env`/`.env.example`/`docker-compose.yml`.

Открытых вопросов нет. Реализация — отдельным шагом/сессией после явного «ок» на старт.
