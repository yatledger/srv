## 2. Симптом и ожидание

Дословная формулировка владельца (после строки итога прогона):

> `ИТОГ: OK — корректностные инварианты выполнены`
> `… ERROR Failed to send request to http://127.0.0.1:35451/raft/append: network error: error sending request`
> `… ERROR Failed to send request to http://127.0.0.1:39885/raft/append: network error: error sending request`
> `… ERROR Failed to send request to http://127.0.0.1:39885/raft/append: network error: error sending request`
> «это тоже немного подбешивает в конце прогона»

**Наблюдаемое.** В конце прогона (при остановке кластера) в stderr появляются `ERROR`-строки о
неудачной отправке Raft RPC на узлы, которые уже гасят HTTP-сервер.

**Ожидаемое.** Штатная недоступность пира не должна выглядеть как ошибка на уровне `ERROR`: для Raft
это нормальная ситуация, он сам ретраит/перевыбирает лидера. В обычном прогоне вывод должен быть
чистым; диагностика недоступности (если нужна) — на `debug`.

## 3. Анализ причины

1. При `cluster.shutdown()` (`src/bin/loadgen/cluster.rs:146-164`) каждому узлу отправляется сигнал
   shutdown, после чего join-ятся потоки. Узлы останавливаются **не одновременно**: пока лидер ещё
   жив, его репликация (`openraft` ReplicationCore) продолжает слать `/raft/append` соседям, чьи
   HTTP-серверы уже остановлены.
2. Обработчик Raft RPC — `src/raft/router.rs:52-55` (до правки):
   ```rust
   let (status, body) = self.http.post_text(&url, &req).await.map_err(|e| {
       error!("Failed to send request to {}: {}", url, e);
       Unreachable::new(&std::io::Error::other(e.to_string()))
   })?;
   ```
   Транспортная ошибка оборачивается в `Unreachable` (то есть для Raft это ожидаемый сигнал
   «недоступен», ведущий к backoff), но **дополнительно** логируется как `error!`.
3. `openraft` сам обрабатывает `RPCError::Unreachable` в `replication/mod.rs:284-285`: логирует на
   уровне `debug` и уходит в backoff. Наш `error!` в роутере дублирует это с завышенным уровнем.

**Корневая причина (формулировка).** Роутер использует уровень `ERROR` для **штатного** для Raft
состояния «пир недоступен» (сеть, рестарт, идущая остановка, выборы). Это не диагностическая ошибка
приложения, а рутинный сигнал для протокола, поэтому он не должен подниматься до `error!`.

**Почему проявлялось именно в `loadgen`.** In-process кластер `loadgen` останавливается в одном
процессе и последовательно, окно «лидер жив — реплика уже погасла» возникает на каждом прогоне. В
`tests/cluster` тот же путь есть, но тестовый вывод не читают глазами.

**Регрессия?** Нет. Код роутера — часть исходной реализации Raft (`A*`), уровень лога не менялся.

## 4. Влияние

- **Наблюдаемость (🔵).** `ERROR`-шум маскирует реальные ошибки и портит демо/нагрузочный вывод.
- **Корректность/данные.** Не затронуты: поведение `Unreachable`/retry/выборов не меняется, канонический
  хэш/подпись, state machine, `SCHEMA_VERSION`, Raft-контракт — без изменений.
- **Тесты.** `tests/cluster` и `cargo test --all` не затронуты; шум исчезает и там.
