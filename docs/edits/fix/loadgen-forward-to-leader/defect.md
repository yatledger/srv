# Дефект: `loadgen` шлёт нагрузку строго лидеру, минуя форвардинг через follower

> Группа: **edits/fix/loadgen-forward-to-leader** · Тип: **fix** · Статус: **реализован, проверки
> пройдены (см. [`report.md`](report.md))**.
> ID задачи: **F4**. Характер: 🔵 · Приоритет: **P3**. Решение владельца: клиент шлёт запросы на
> **случайный узел** кластера, не-лидер перенаправляет их лидеру; в выводе виден узел и роль.

## 2. Симптом и ожидание

Дословная формулировка владельца (разбор блока живого вывода, где всегда был один и тот же адрес):

> «раз мы поднимаем N нод — то фактически мы же можем отправлять запрос на любую из них, а она уже
> должна перенаправлять его лидеру..? так давай так и сделаем то есть рандомно на любую ноду из
> кластера отправлять запросы с соответствующим отображением в выводе»

**Наблюдаемое.** `runner.rs` определял лидера (`resolve_leader`) и все запросы отправлял **строго ему**;
в пофреймовом выводе всегда фигурировал один и тот же адрес. Публичный путь клиента
«запрос → follower → форвардинг лидеру» (`server.rs::add_tx`) инструментом **не проверялся**.

**Ожидаемое.** Запросы распределяются по случайным узлам кластера; запись, пришедшая на не-лидера,
перенаправляется лидеру; инструмент по-прежнему подтверждает корректность (все валидные tx приняты,
реплики совпадают), а в выводе виден узел-приёмник и его роль.

## 3. Анализ причины

Цепочка вызовов (до правки):

1. `src/bin/loadgen/runner.rs:92` — `let leader = resolve_leader(nodes).await?;` — разово определяется
   URL лидера.
2. `src/bin/loadgen/runner.rs:163` — `fetch_pool(&client, leader)` — родители берутся из `/pool`
   **лидера**.
3. `src/bin/loadgen/runner.rs:229` — `send_with_retry(&client, leader, …)` — каждый запрос POST-ится
   на **лидера**.
4. `src/server.rs:178` — на лидере ветка `if leader_id == app.id` уходит в `add_handler` напрямую;
   ветка форвардинга (`server.rs:182-237`) в нагрузочном прогоне **никогда не исполнялась**.

**Корневая причина (формулировка).** Инструмент (задуманный как проверка корректности кластера)
искусственно сузил клиентский путь до прямого обращения к лидеру. Это не ломало корректность
инструмента, но оставляло вне проверки (а) перенаправление follower → лидер и (б) раннюю валидацию
состояния (`tx_logic::validate_against_state`) на отстающей реплике — ровно тот путь, которым идут
внешние клиенты.

**Почему нельзя было просто «слать на любой узел».** Модульный комментарий `runner.rs` фиксировал
причину отправки лидеру: follower может ещё не применить свежие родители, и его ранняя проверка
состояния ложно отклонила бы валидную транзакцию. Поэтому наивная рандомизация узла при родителях из
`/pool` лидера давала бы ложные `409`. Корректный фикс обязан брать родителей из `/pool` **того же**
узла, которому шлём.

**Регрессия?** Нет. Такое поведение было изначальным дизайном `N01`, а не регрессией закрытой задачи.

## 4. Влияние

- **Проверочное покрытие.** Инструмент перестаёт быть «чёрным ящиком на лидере» и упражняет публичный
  путь клиента, включая форвардинг и раннюю валидацию на follower.
- **Диагностика.** Живой вывод показывает роль узла (`лидер` / `follower → лидер`), видно распределение.
- **Корректность/данные.** Не затронуты: канонический хэш/подпись, `added`/уникальность, контракт
  Raft-типов, `SCHEMA_VERSION`, state machine. Все валидные tx по-прежнему принимаются, реплики
  сходятся.
- **Производительность.** У не-лидера добавляется один внутренний хоп форвардинга: p95/p99 растут
  (наблюдалось p95 ~0.7 с при `--tx 300 --concurrency 8` против прямых запросов). Для
  информационных метрик приемлемо; TPS-ориентированные замеры по-прежнему не SLA.

## 6. Открытые вопросы владельцу

Решено владельцем 2026-10-09:

1. **Область.** Случайный узел — на **все** прогоны (демо и явные флаги), не только демо.
2. **Отображение.** В выводе показывать узел **и** роль (`node`/`follower → лидер`).
3. **Корректность.** Родители берутся из `/pool` целевого узла, чтобы ранняя проверка не давала
   ложный отказ.

Открытых вопросов нет.
