## 2. Симптом и ожидание

Дословная формулировка владельца:

> `NODE_ID=4 HTTP_PORT=21004 DATA_DIR=./data/node4 ./target/release/dagdb`
> `… startup done: id=4 …`
> `… dagdb::server: Server running at 0.0.0.0:21001`
> «я передаю HTTP_PORT=21004, dagdb::server: Server running at 0.0.0.0:21001»

**Наблюдаемое.** Узел получает `NODE_ID=4`, но HTTP-сервер слушает `0.0.0.0:21001`, а не `21004`.
Команда совпадает с документированной в `README.md:149-153` локальной инструкцией запуска узлов 2–4,
поэтому узел 4 «залипает» на адресе узла 1.

**Ожидаемое.** Явно переданный `HTTP_PORT=21004` (как и `--port 21004`) должен определять порт
прослушивания — либо, если это осознанно невозможно из-за приоритета `BIND_ADDR`, узел должен
**явно сказать** об этом в логе, а не молча открыть другой порт.

## 3. Анализ причины

Цепочка вызовов:

1. `src/main.rs:34` — `AppConfig::load()`.
2. `src/config.rs:175-179` — `load()` вызывает `dotenvy::dotenv()`. Функция ищет `.env` **от текущего
   рабочего каталога вверх** и загружает найденный. При запуске из корня репозитория это
   `/home/pin/dev/yat/srv/.env`; в нём (создан из `.env.example`) заданы
   `BIND_ADDR=0.0.0.0:21001`, `HTTP_PORT=21001` и `ADVERTISE_ADDR=127.0.0.1:21001`.
3. `dotenvy` **не перезаписывает** уже установленные переменные процесса (`override=false`). Поэтому
   переданные в командной строке `NODE_ID=4`, `HTTP_PORT=21004`, `DATA_DIR=./data/node4` сохранены,
   а отсутствующий в окружении `BIND_ADDR` — **добавлен из `.env`** как `0.0.0.0:21001`.
4. `src/config.rs:181-186` — **корневое место**:
   ```rust
   pub fn bind_addr(&self) -> String {
       self.bind_addr
           .clone()
           .unwrap_or_else(|| format!("0.0.0.0:{}", self.port))
   }
   ```
   `BIND_ADDR` имеет приоритет над `port`. Раз `self.bind_addr = Some("0.0.0.0:21001")`, значение
   `self.port = 21004` не используется.
5. `src/main.rs:66` — `server::start_server(app.clone(), cfg.bind_addr())`;
   `src/server.rs:937` — `TcpListener::bind("0.0.0.0:21001")`; `src/server.rs:939` — лог
   `Server running at 0.0.0.0:21001`.
6. Аналогично `src/config.rs:188-193` `advertise_addr()` берёт `ADVERTISE_ADDR` из `.env`
   (`127.0.0.1:21001`), поэтому узел 4 **объявляет кластеру адрес узла 1** — потенциальная коллизия
   идентичности в локальном кластере.

**Почему «молча».** Явного предупреждения о том, что `BIND_ADDR` перекрывает `HTTP_PORT`/`--port`, нет.
`NODE_ID` при этом берётся корректно, что маскирует причину: пользователь видит правильный `id=4` и
неверный порт.

**Проверено экспериментами** (из корня репозитория, `.env` с `BIND_ADDR=0.0.0.0:21001`):

| Команда (env + аргументы) | Наблюдаемый bind | Вывод |
|---|---|---|
| `env NODE_ID=8 HTTP_PORT=21004 ... dagdb` | `0.0.0.0:21001` | `HTTP_PORT` игнорируется — воспроизведение |
| `env NODE_ID=8 HTTP_PORT=21004 ... dagdb --port 21005` | `0.0.0.0:21001` | `--port` тоже игнорируется, если задан `BIND_ADDR` |
| `env NODE_ID=8 BIND_ADDR=0.0.0.0:29998 ... dagdb` | `0.0.0.0:29998` | переданный извне `BIND_ADDR` работает |
| `env NODE_ID=8 BIND_ADDR=0.0.0.0:29999 HTTP_PORT=21004 ... dagdb` | `0.0.0.0:29999` | победитель — всегда `BIND_ADDR` |

**Корневая причина (формулировка).** Конфигурация, исторически рассчитанная на **один** узел,
задаёт `BIND_ADDR` (и `ADVERTISE_ADDR`/`HTTP_PORT`/`NODE_ID`/`DATA_DIR`) в `.env`, который
подхватывается из CWD и применяется ко **всем** узлам. При этом `AppConfig::bind_addr()` отдаёт
`BIND_ADDR` безусловный приоритет над `HTTP_PORT`/`--port`, а расхождение никак не диагностируется.
Документированная в `README.md` локальная инструкция для узлов 2–4, передающая `HTTP_PORT`, в такой
конфигурации неработоспособна.

**Регрессия?** Нет регрессии конкретного поведения: и `BIND_ADDR`, и узлоспецифичные ключи появились
в рамках `K1` (`3c59c6d`, «загружать конфигурацию из окружения»). Это дефект дизайна конфигурации и
документации, существующий с момента перехода на `.env`.

## 4. Влияние

- **Локальная разработка (🟠).** Запуск кластера узлов 2–4 по README невозможен без ручной правки
  `.env`; каждый узел пытается занять `21001`.
- **Идентичность/маршрутизация.** `ADVERTISE_ADDR` из `.env` заставляет узел 4 анонсировать адрес
  узла 1 — при живом узле 1 это коллизия в membership/router, вводящая в заблуждение при отладке.
- **Диагностика.** Симптом («я передаю порт, он игнорируется») не сопровождается предупреждением.
- **Детерминизм/целостность/данные.** Не затронуты: канонический хэш/подпись, `added`/уникальность,
  контракт Raft-типов, `SCHEMA_VERSION`, state machine. `DATA_DIR` из командной строки применяется
  корректно (он есть в окружении процесса), поэтому данные не смешиваются.
