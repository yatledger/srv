# План устранения: `HTTP_PORT` игнорируется из-за `BIND_ADDR` в `.env` (F2)

> Группа: **edits/fix/http-port-ignored** · Тип: **fix** · Статус: **план на согласовании**.
> Решения по контракту — за владельцем (см. [`defect.md`](defect.md) §6).
> Ссылки: [`defect.md`](defect.md) (паспорт дефекта), [`tracker.md`](tracker.md), [`report.md`](report.md).
> Исходный код на этом шаге **не меняется** — реализация после согласования.

## 1. Цель и границы

**Чиним.** Локальный запуск нескольких узлов должен работать предсказуемо, а расхождение
`BIND_ADDR` ↔ `HTTP_PORT`/`--port` — не теряться молча. Владелец должен либо получить ожидаемый порт,
либо явную диагностику, указывающую, какое значение и откуда победило.

**В скоупе:**
- `src/config.rs` — определить и реализовать контракт приоритета при конфликте `BIND_ADDR` и
  `HTTP_PORT`/`--port`; добавить диагностику конфликта.
- `.env.example` — убрать/переработать узлоспецифичные `BIND_ADDR`/`HTTP_PORT`/`ADVERTISE_ADDR`, чтобы
  дефолтный `.env` не фиксировал «узел 1» для всех.
- `README.md` — синхронизировать инструкцию локального запуска с фактическим контрактом (и пояснить,
  как задавать узлы, не редактируя общий `.env`).

**Вне скоупа (осознанно):**
- Полноценный механизм оверрайда env-файла (`--env-file`/`DOTENV_PATH`) — предлагается только как
  опция; если владелец выберет, оформляется отдельным пунктом/задачей.
- Изменения state machine, Raft-контракта, канонического хэша/подписи, `SCHEMA_VERSION`, публичного/
  внутреннего API.

## 2. Требования к поведению после фикса

Точный контракт — решение владельца; рекомендуемый вариант выделен.

1. **Рекомендуется (предсказуемость для мультиузла): явный `HTTP_PORT`/`--port` побеждает `.env`-ный
   `BIND_ADDR`.** Тогда README-команда `NODE_ID=4 HTTP_PORT=21004 …` открывает `0.0.0.0:21004`, как и
   ожидает пользователь. `BIND_ADDR`, заданный **в процессе/CLI**, по-прежнему перекрывает всё
   (максимальная специфичность).
   - Альтернатива A: оставить `BIND_ADDR` безусловным приоритетом, но **логировать предупреждение**
     `BIND_ADDR=… перекрывает HTTP_PORT=…` и **исправлять docs/`.env.example`**, убрав из дефолтного
     `.env` узлоспецифичные ключи.
   - Альтернатива B: считать конфликт `BIND_ADDR` ↔ `HTTP_PORT` **ошибкой валидации** (жёстко в
     `stage`/`prod`, предупреждение в `dev`).
2. **Диагностика.** При любом расхождении — запись в лог с указанием источника победившего значения
   (env/CLI/`.env`/default), без утечки секретов.
3. **Совместимость.** `bind_addr()/advertise_addr()` сохраняют поведение для случая, когда задан
   только один источник; happy-path одного узла не ломается.
4. **Инварианты не задеты.** Формат состояния/лога, API, хэш/подпись, `SCHEMA_VERSION` не меняются.

## 4. Шаги реализации (порядок)

1. **Решение владельца** по контракту (§2, §8) — зафиксировать в этом файле/`tracker.md`.
2. **Код.** Реализовать приоритет и диагностику в `src/config.rs`; при необходимости отличать
   «`HTTP_PORT` задан явно» от дефолта (например, `Option<u16>` с геттером, возвращающим эффективный
   порт). Не менять прочие параметры.
3. **Docs/config.** Обновить `.env.example` и `README.md` под выбранный контракт.
4. **Тесты.** См. §5 — обязательный регрессионный тест на воспроизведённый дефект.
5. **Проверки.** `cargo fmt --all`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all`
   (Redis для интеграционных), `cargo bench --no-run`.
6. **Ручная проверка.** Из корня репозитория с `.env`, содержащим `BIND_ADDR`: команда
   `NODE_ID=8 HTTP_PORT=21004 … dagdb` должна дать ожидаемый bind (или явное предупреждение — по
   выбранному контракту).

## 5. Тесты

- **Модульные (`src/config.rs`).** Юнит-тест на выбранный контракт: `BIND_ADDR` в конфиге + явный
  `HTTP_PORT` → ожидаемый `bind_addr()`; конфликт → предупреждение/ошибка (в зависимости от решения).
- **Регрессионный (обязателен).** Воспроизводит исходный дефект: при `bind_addr = Some("…:21001")` и
  `port = 21004` `bind_addr()` больше **не** возвращает `21001` молча. Тест должен **падать до фикса**
  и **проходить после**.
- **Диагностика.** Тест (или фиксация ручной проверкой), что при конфликте логируется источник
  победившего значения.
- **Интеграционные:** `tests/api`/`tests/cluster` не ломать (они собирают `AppConfig` в фабрике —
  учесть изменение полей, если `port` станет `Option`).

> Примечание: выбранный контракт может потребовать изменить тип поля `port` (например,
> `Option<u16>`), что затронет фабрики `AppConfig` в `tests/` и `src/lib.rs` (тест F1). Это
> механическое изменение — перечислить в отчёте.

- [ ] Инварианты (`AGENTS.md` §6) не затронуты; `SCHEMA_VERSION` не менялся.

## 7. Риски и откат

| Риск | Митигация |
|---|---|
| Смена приоритета (`HTTP_PORT` побеждает `BIND_ADDR`) может неожиданно изменить поведение тех, кто задаёт оба в проде | Не менять приоритет **внутрипроцессного** `BIND_ADDR` (он остаётся главным); менять/диагностировать только случай `.env`; при сомнении предпочесть вариант «предупреждение» вместо смены приоритета. |
| Изменение типа `port` (`u16` → `Option<u16>`) задевает фабрики тестов/`lib.rs` | Механические правки, покрыть `cargo test --all`; отдельным коммитом от логики (AGENTS.md §4). |
| Слишком шумные предупреждения | Логировать один раз при старте, только при реальном конфликте. |

**Откат.** Правка локальна (`config.rs`, docs); откат — `git revert`. Миграции состояния/
`SCHEMA_VERSION` не требуются.
