## 4. Методология и инструменты

Чтобы повторный аудит был сопоставим, используй те же проверки:

```bash
# 1. Собираемость и статический анализ
cargo check
cargo clippy --all-targets

# 2. Тесты
cargo test --all

# 3. Метрики «запахов» кода
grep -rEn '\.unwrap\(\)|\.expect\(|panic!|todo!|unimplemented!' src | wc -l
grep -rn 'TODO\|FIXME\|HACK\|XXX' src
grep -rn 'unsafe' src
grep -rEn 'redis://|http://|password|secret|token' src
```

**Критерии классификации (сохранять преемственность):**
- 🔴 — ломает безопасность/данные/работу, падение узла, утечка секретов.
- 🟠 — серьёзный недочёт, мешает корректной/предсказуемой работе.
- 🟡 — качество/удобство/сопровождаемость.
- 🔵 — важный отсутствующий компонент (тесты, наблюдаемость, спецификация...).

**Область аудита по умолчанию:** `src/`, `Cargo.toml`, `genesis.json`, `tests/`, инфраструктура
(`Dockerfile`, compose, CI, env). Папку `to/` аудировать как черновик — только отмечать факт наличия.

## 8. Открытые вопросы и допущения первого аудита

Владельцу проекта стоит подтвердить/опровергнуть (аудитору — учитывать):

1. **Целевая платформа:** реальный блокчейн/леджер или учебный/внутренний прототип?
   От этого зависит глубина требований (TLS, аудит, соответствие).
2. **Redis:** обязательная зависимость или временное решение? Есть ли альтернатива (встроенное
   персистентное хранилище)?
3. **Формат `func`:** планируется один `transferToken` или реестр функций? Нужен ли ABI/реестр.
4. **Модель валидации `var`:** фиксированная схема (`TxVar`) или произвольный JSON?
   Влияет на K2/K4.
5. **Хранилище для K5:** предпочтение по движку (RocksDB / sled / redb).
6. **API-контракт:** предполагается строгая версия/схема ответов (для V5)?
7. **Аутентификация узлов (K3):** общий токен, mTLS или подпись запроса ключом узла?
8. **Персистентность `added`:** допустим ли TTL или требуется полный реестр (V1)?

Если ответы получены — внеси их сюда и в соответствующие ТЗ.
