# Скилл: разбор дефекта и план фикса `dagdb`

Переиспользуемая методика: **принять описанную владельцем ошибку → локализовать корневую причину по
коду → оформить задачу `fix` с планом устранения**. Подходит для багов, регрессий и инцидентов.

> Скилл **только диагностирует и документирует**. Исходный код (`src/`, `tests/`, `Cargo.toml`,
> инфраструктура) в рамках этого шага **не меняется** — сначала согласованный план, реализация —
> отдельным шагом/сессией. Так мы не смешиваем анализ и правку и не ломаем инварианты «на лету».

## 0. Как пользоваться

1. Открой сессию в корне репозитория `/home/pin/dev/yat/srv`.
2. Прочитай регламент и контекст (раздел 1).
3. Прими и при необходимости уточни дефект (раздел 2).
4. Проведи диагностику и найди корневую причину (раздел 3).
5. Заведи папку `docs/edits/fix/<slug>/` и оформи задачу (раздел 5).
6. Согласуй план владельцем — реализация идёт после «ок».

## 1. Обязательное чтение перед началом

- [`AGENTS.md`](../../../AGENTS.md) — инварианты, критические зоны, workflow, подводные камни.
- [`docs/README.md`](../../../docs/README.md) — карта документации.
- [`docs/edits/fix/README.md`](../../../docs/edits/fix/README.md) — формат задач `fix/`.
- Прошлые аудиты и фиксы: `docs/edits/audit/*/`, `docs/edits/fix/*/` — чтобы понять, **не чинится ли
  это уже** и не является ли ошибка регрессией закрытой задачи (проверь `tracker.md` аудитов и
  `git log`).
- При существенной правке — `docs/edits/feature/*/` (не конфликтует ли с планами).

Если дефект заведён как находка аудита (`S*`/`D*`/`C*`) — найди её формулировку в
`docs/edits/audit/<slug>/audit.md` и ссылайся на ID, а не пересказывай заново.

## 2. Приём дефекта

Минимум, что нужно от владельца (спроси недостающее, не домысливай — см. раздел 8):

1. **Что не так.** Наблюдаемое поведение vs ожидаемое.
2. **Как воспроизвести.** Запрос/команда/сценарий, окружение (профиль, число узлов, версия/коммит).
3. **Артефакты.** Логи, трейс, код ответа, `x-request-id`, дамп — что есть.
4. **Источник.** Свободное наблюдение / находка аудита (`ID`) / регрессия после коммита `…`.
5. **Серьёзность на взгляд владельца** (предварительно; окончательную — определи сам, раздел 4).

Зафиксируй дословную формулировку владельца в `defect.md` — она пригодится при сверке результата.

## 3. Методология диагностики

```bash
# 0. База и рабочие изменения
git log --oneline -20 && git status

# 1. Где вообще живёт подозрительная логика (домен → raft → server)
grep -rn '<симптом/ключевое слово>' src tests docs/api

# 2. Собираемость и статика
cargo check --all-targets
cargo clippy --all-targets -- -D warnings

# 3. Тесты (интеграционные требуют Redis — подними или явно отметь)
docker run -d --name dagdb-redis -p 6379:6379 redis:7-alpine
cargo test --all
```

**Воспроизведение.** По возможности воспроизведи дефект до правки: через существующий тест,
`curl` к локальному узлу, `test.sh`, мини-сценарий в `/tmp/opencode` (**вне репозитория**). Если
для воспроизведения нужен новый тест — опиши его в плане как регрессионный и заведи там же, а не
добавляй тест в `src/` на этом шаге. Если воспроизвести нельзя — честно зафиксируй это и зови
владельца за деталями.

**Локализация причины.** Веди цепочку от симптома к источнику:
`HTTP-граница (server.rs) → tx_logic → Raft.client_write → apply (raft/store.rs) → домен (graph/, domain.rs)`.
Для каждого звена фиксируй `файл:строка` и что там происходит. Отличай **симптом** от **корневой
причины** (напр. «500 у клиента» — симптом; «ошибка SM не проверяется в handler» — корень).

**Проверка полноты.** Пойми:
- зависит ли баг от одной реплики/лидера/сети/времени — недетерминизм особенно опасен (см. инварианты);
- проходит ли исправление через **детерминированный state machine** (валидация не должна зависеть
  от времени/сети);
- не задевает ли фикс **канонический хэш/подпись**, `added`/уникальность хэша, контракт Raft-типов,
  `SCHEMA_VERSION` (при смене формата — версия + миграция), разделение публичного/внутреннего API;
- есть ли **другие места** с той же ошибкой (поиск по шаблону), а не только одно.

## 4. Классификация

**Характер** (та же шкала, что в аудите):

- 🔴 — ломает безопасность/целостность данных, падение узла, утечка секретов.
- 🟠 — серьёзный дефект, мешает корректной/предсказуемой работе.
- 🟡 — качество/удобство/сопровождаемость.
- 🔵 — отсутствует важное (тест, проверка, наблюдаемость…).

**Приоритет:** P0 (немедленно) · P1 · P2 · P3 · P4 (когда-нибудь).
Регрессию помечай ⚠️ и указывай коммит/задачу, которая её внесла.

## 5. Оформление задачи

Создай новую папку `docs/edits/fix/<slug>/` (например, `docs/edits/fix/add-4xx/`). Рекомендуемое
содержимое:

- **`defect.md`** — паспорт дефекта: заголовок, сводка, характер/приоритет, источник, окружение и
  коммит, шаги воспроизведения, ожидаемое/фактическое, артефакты, **анализ причины** (`файл:строка`
  и цепочка), влияние на инварианты, связи с аудитом.
- **`plan.md`** — план устранения: цель, технические требования, **затрагиваемые файлы**, шаги,
  изменения в тестах (включая регрессионный тест), DoD, риски/план отката, порядок, что вне скоупа.
- **`tracker.md`** — сводный трекер: список файлов задачи, таблица `ID → задача → характер →
  приоритет → статус`, журнал изменений.
- **`report.md`** — **заготовка** отчёта о реализации (кто, коммит-база, изменённые файлы, пройденные
  проверки, отклонения от плана). Заполняется на этапе реализации, а не в этом скилле.

В начале каждого документа — пометка (группа `edits/fix/<slug>`, тип `fix`, статус) и ссылки на
соседей относительными путями. Новую папку добавь в [`docs/edits/fix/README.md`](../../../docs/edits/fix/README.md).

### Формат `defect.md`

1. **Сводка:** заголовок, дата, коммит, серьёзность, кто сообщил.
2. **Симптом и ожидание:** воспроизведение шаг-за-шагом, наблюдаемое vs ожидаемое, артефакты.
3. **Анализ причины:** цепочка вызовов с `файл:строка`, точная корневая причина.
4. **Влияние:** какие сценарии/инварианты задеты, подвержены ли данные/безопасность/детерминизм.
5. **Связи:** ID находки аудита, задача-первопричина (регрессия?), дублирующие места.
6. **Открытые вопросы** владельцу.

### Формат `plan.md`

1. **Цель и границы** (что чиним, что осознанно не чиним).
2. **Требования** к поведению после фикса (в терминах контракта API/инвариантов).
3. **Затрагиваемые файлы** (список с пояснением роли).
4. **Шаги реализации** в порядке выполнения.
5. **Тесты:** какие юнит/интеграционные добавить; обязательный регрессионный тест на дефект.
6. **DoD:** наблюдаемое исправление + `cargo fmt`/`clippy -D warnings`/`test --all` зелёные (Redis
   для интеграционных) + инварианты не нарушены.
7. **Риски и откат:** что может пойти не так, как откатывать, нужна ли миграция/подъём `SCHEMA_VERSION`.
8. **Открытые вопросы / решения владельца.**

## 6. Составление плана: ориентиры по проекту

- **Минимальность и точечность.** Чини корень, а не симптом; не смешивай фикс с рефакторингом или
  форматированием (разные коммиты).
- **Детерминизм.** Любая валидация в state machine должна быть одинаковой на всех репликах и не
  зависеть от сети/часов; ошибки apply должны доходить до клиента `4xx` (`ApplyResult`), а не `200`.
- **Инварианты** (`AGENTS.md`): не менять канонический хэш/подпись без явного решения; сохранять
  семантику `added` и уникальность хэша; не ослаблять разделение публичного/внутреннего API; при
  изменении формата состояния — поднимать `SCHEMA_VERSION` и добавлять миграцию.
- **Тесты.** Предпочитай детерминированный юнит-тест; для путей через Raft/HTTP — интеграционный.
  Регрессия обязательна: тест должен падать до фикса и проходить после.

## 7. Соглашения по ID и трекеру

- Задача дефекта получает ID `F<NN>` (следующий свободный, сквозной по `docs/edits/fix/`); шаги/подзадачи
  — `F<NN>.<k>`. ID не переиспользуются.
- Ссылка на источник: ID находки аудита (`C34`, `S16`, …), коммит (`abc1234`) или формулировка владельца.
- Изменение статусов (`⬜`/`🔄`/`✅`) — в `tracker.md` соответствующей папки, отдельным `docs:` коммитом.
- Коммиты реализации — Conventional Commits (`fix(scope): …`) с `Refs: F<NN>` в теле.

## 8. Типовые открытые вопросы владельцу

1. **Ожидаемое поведение** — что именно считается «исправлено» (код ответа, состояние графа, лог).
2. **Область** — чинить только этот путь или искать и устранять везде, где встречается паттерн?
3. **Совместимость** — допустимы ли изменение формата состояния/ответа и миграция?
4. **Приоритет и сроки** — тянуть в текущую итерацию или только зафиксировать план?
5. **Воспроизведение** — есть ли у владельца окружение/данные, которых нет у агента.
6. **Решение по спорным местам** — если симптом можно погасить по-разному, какой контракт считаем верным.
