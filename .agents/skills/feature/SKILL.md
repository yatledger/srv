# Скилл: проектирование фичи и план реализации `dagdb`

Переиспользуемая методика: **принять от владельца идею новой возможности → уточнить её наводящими
вопросами → спроектировать решение по коду → оформить задачу `feature` с ТЗ и планом реализации**.
Подходит для новых эндпоинтов, функций, эксплуатационных возможностей, изменений конфигурации и т.п.

> Скилл **только проектирует и документирует**. Исходный код (`src/`, `tests/`, `Cargo.toml`,
> инфраструктура) в рамках этого шага **не меняется** — сначала согласованное ТЗ/план, реализация —
> отдельным шагом/сессией. Так мы не смешиваем проектирование и правку и не ломаем инварианты «на лету».

## 0. Как пользоваться

1. Открой сессию в корне репозитория `/home/pin/dev/yat/srv`.
2. Прочитай регламент и контекст (раздел 1).
3. Прими идею фичи и **задай наводящие вопросы** (раздел 2) — не домысливай.
4. Изучи существующий код/API в предполагаемой области (раздел 3).
5. Заведи папку `docs/edits/feature/<slug>/` и оформи задачу (раздел 5).
6. Согласуй ТЗ/план с владельцем — реализация идёт после «ок».

## 1. Обязательное чтение перед началом

- [`AGENTS.md`](../../../AGENTS.md) — инварианты, критические зоны, workflow, подводные камни.
- [`docs/README.md`](../../../docs/README.md) — карта документации.
- [`docs/edits/feature/README.md`](../../../docs/edits/feature/README.md) — формат задач `feature/` и
  список уже заведённых фич.
- [`docs/api/API.md`](../../../docs/api/API.md) и [`docs/api/openapi.json`](../../../docs/api/openapi.json) —
  если фича трогает публичный HTTP-контракт.
- Прошлые фичи и фиксы: `docs/edits/feature/*/`, `docs/edits/fix/*/` — чтобы понять, **не реализуется
  ли это уже** и не является ли идея частью ранее отложенной задачи (`report.md` → «что дальше»).
- Прошлые аудиты: `docs/edits/audit/*/` — не противоречит ли фича принятым решениям и не дублирует
  ли отложенные находки (`S*`/`D*`/`C*`).

Если идея уже зафиксирована как отложенная задача (напр. во `fix/*` или `audit/*` со статусом
«вне скоупа / отдельная feature») — ссылайся на неё по ID, а не пересказывай заново.

## 2. Приём фичи и наводящие вопросы

Прежде чем писать план, **обязательно выясни у владельца** недостающее. Не домысливай требования.
Базовый набор вопросов (задавай те, что не ясны из описания; ответы фиксируй в `spec.md`/`plan.md`):

1. **Цель и сценарий использования.** Какую проблему решает фича? Кто пользователь (внешний клиент,
   эксплуатация, другая подсистема) и какой user story / конкретный кейс? Что считается успехом?
2. **Границы и не-цели.** Что входит в скоуп, а что осознанно **вне** него (чтобы не раздувать
   задачу)? Есть ли MVP vs полный вариант?
3. **Контракт API/поведение.** Новые/изменённые endpoints, методы, коды ответов, формат тела; публичный
   или внутренний API (см. инвариант разделения, `AGENTS.md` §6). Какие ошибки и граничные случаи?
4. **Данные/совместимость.** Затрагивает ли формат состояния/лога, `SCHEMA_VERSION`, канонический
   хэш/подпись, контракт Raft-типов? Нужна ли обратная совместимость и миграция? Новые env/CLI-параметры?
5. **Приоритет и этапность.** Характер (раздел 4), приоритет P0–P4, что делаем сейчас, а что позже.
6. **Ограничения и риски.** Безопасность, производительность, эксплуатация, TLS, зависимости
   (Redis), нагрузка — всё, что может сузить решение.

Зафиксируй дословную формулировку владельца в `spec.md` — она пригодится при сверке результата.

## 3. Анализ области и проектирование

```bash
# 0. База и рабочие изменения
git log --oneline -20 && git status

# 1. Где живёт похожая логика (домен → raft → server → config)
grep -rn '<ключевое слово фичи>' src tests docs/api

# 2. Собираемость и статика
cargo check --all-targets
cargo clippy --all-targets -- -D warnings
```

**Где искать точки интеграции.** Веди цепочку по слоям и фиксируй `файл:строка`:
`HTTP-граница (server.rs) → auth.rs (публичный/внутренний) → tx_logic → Raft.client_write → apply
(raft/store.rs) → домен (graph/, domain.rs)`; для эксплуатационных фич — `config.rs`, `metrics.rs`,
`cleanup.rs`, `shutdown.rs`, `scripts/`.

**Проектирование.** Для выбранной идеи опиши:
- минимальный набор изменений и **переиспользование** существующих механизмов (не плоди дубли);
- альтернативы решения и почему выбран рекомендуемый вариант;
- **влияние на инварианты** (`AGENTS.md` §6): канонический хэш/подпись, детерминированный state
  machine, `added`/уникальность хэша, разделение публичного/внутреннего API, контракт Raft-типов,
  версионирование `SCHEMA_VERSION` (при смене формата — версия + миграция);
- путь данных «запись → пересылка лидеру → apply на всех репликах» и где в нём встраивается фича;
- что должно быть детерминировано (валидация в state machine не зависит от сети/часов);
- какие тесты (юнит/интеграционные/бенчмарки) и docs (README, `.env.example`, `docs/api/`) потребуются.

**Проверка полноты.** Пойми:
- не конфликтует ли фича с прошлыми решениями (`audit`/`fix`/`feature`);
- нет ли уже частичной реализации (поиск по API/метрикам/config);
- можно ли разбить на этапы так, чтобы каждый был самостоятельно проверяем.

## 4. Классификация

**Характер** (та же шкала, что в аудите и fix):

- 🔴 — затрагивает безопасность/целостность данных, критическую доступность, секреты.
- 🟠 — крупная/рискованная возможность, требует аккуратной интеграции с ядром.
- 🟡 — обычная возможность, качество/удобство/сопровождаемость.
- 🔵 — вспомогательное/инфраструктурное (наблюдаемость, спецификация, тесты...).

**Приоритет:** P0 (немедленно) · P1 · P2 · P3 · P4 (когда-нибудь).

**Тип изменения контракта:** аддитивное (не ломает существующее) или breaking (нужна миграция/
версионирование) — помечай явно.

## 5. Оформление задачи

Создай новую папку `docs/edits/feature/<slug>/` (например, `docs/edits/feature/redis-lazy-connect/`).
Рекомендуемое содержимое:

- **`spec.md`** — ТЗ/паспорт фичи: заголовок, сводка, характер/приоритет, источник и формулировка
  владельца, проблема и сценарий использования, требования (в терминах контракта API/поведения),
  границы и **не-цели**, влияние на инварианты/совместимость, связи с аудитами/фиксами/фичами,
  открытые вопросы.
- **`plan.md`** — план реализации: цель и границы, **затрагиваемые файлы**, шаги в порядке выполнения,
  изменения в тестах, изменения в docs/`.env.example`/OpenAPI, DoD, риски/план отката (в т.ч.
  миграция/подъём `SCHEMA_VERSION` при необходимости), этапность, что вне скоупа.
- **`tracker.md`** — сводный трекер: список файлов задачи, таблица `ID → задача → характер →
  приоритет → статус`, журнал изменений.
- **`report.md`** — **заготовка** отчёта о реализации (кто, коммит-база, изменённые файлы, пройденные
  проверки, отклонения от плана). Заполняется на этапе реализации, а не в этом скилле.

В начале каждого документа — пометка (группа `edits/feature/<slug>`, тип `feature`, статус) и ссылки
на соседей относительными путями. Новую папку добавь в
[`docs/edits/feature/README.md`](../../../docs/edits/feature/README.md).

### Формат `spec.md`

1. **Сводка:** заголовок, дата, коммит-база, характер/приоритет, тип (аддитивное/breaking), кто (заказчик).
2. **Проблема и сценарий:** дословная формулировка владельца, user story/кейсы, зачем это нужно.
3. **Требования:** функциональные, в терминах контракта API/поведения (входы/выходы, коды, ошибки,
   граничные случаи); публичный vs внутренний API.
4. **Границы и не-цели:** что входит и что осознанно вне скоупа; MVP vs полный вариант.
5. **Влияние:** инварианты (`AGENTS.md` §6), совместимость, `SCHEMA_VERSION`/миграции, конфиг/env,
   производительность/безопасность/эксплуатация.
6. **Связи:** отложенные задачи аудита/фикса, родственные фичи, дубли.
7. **Открытые вопросы** владельцу.

### Формат `plan.md`

1. **Цель и границы.**
2. **Требования** к поведению после реализации (контракт API/инварианты).
3. **Затрагиваемые файлы** (список с пояснением роли).
4. **Шаги реализации** в порядке выполнения (при необходимости — по этапам с независимой проверкой).
5. **Тесты:** какие юнит/интеграционные/бенчмарки добавить; что именно проверяем.
6. **Docs:** что обновить (`README.md`, `.env.example`, `docs/api/API.md`, `docs/api/openapi.json`).
7. **DoD:** наблюдаемый результат + `cargo fmt`/`clippy -D warnings`/`test --all` зелёные (Redis для
   интеграционных) + инварианты не нарушены (+ миграция, если менялся формат).
8. **Риски и откат:** что может пойти не так, как откатывать, нужна ли миграция/подъём `SCHEMA_VERSION`.
9. **Этапность и вне скоупа.**
10. **Открытые вопросы / решения владельца.**

## 6. Составление плана: ориентиры по проекту

- **Минимальность.** Переиспользуй существующие механизмы; не смешивай фичу с рефакторингом или
  форматированием (разные коммиты). Аддитивное изменение предпочтительнее breaking.
- **Детерминизм.** Любая логика в state machine должна быть одинаковой на всех репликах и не зависеть
  от сети/часов; ошибки apply должны доходить до клиента `4xx` (`ApplyResult`), а не `200`.
- **Инварианты** (`AGENTS.md` §6): не менять канонический хэш/подпись без явного решения; сохранять
  семантику `added` и уникальность хэша; не ослаблять разделение публичного/внутреннего API; при
  изменении формата состояния — поднимать `SCHEMA_VERSION` и добавлять миграцию.
- **Границы API.** Новые внутренние endpoints — под `x-internal-token`, публичные — осознанно
  добавляются в `server.rs`, документацию и `openapi.json`.
- **Тесты.** Предпочитай детерминированный юнит-тест; для путей через Raft/HTTP — интеграционный
  (Redis обязателен). Для горячих путей — бенчмарк. Фича без теста не считается готовой.

## 7. Соглашения по ID и трекеру

- Задача фичи получает ID `N<NN>` (следующий свободный, сквозной по `docs/edits/feature/`); шаги/
  подзадачи — `N<NN>.<k>`. ID не переиспользуются.
- Ссылка на источник: формулировка владельца, ID находки аудита (`C34`, `S16`, …), ID фикса (`F1`, …)
  или отложенная задача.
- Изменение статусов (`⬜`/`🔄`/`✅`) — в `tracker.md` соответствующей папки, отдельным `docs:` коммитом.
- Коммиты реализации — Conventional Commits (`feat(scope): …`) с `Refs: N<NN>` в теле.

## 8. Типовые открытые вопросы владельцу

1. **Цель и сценарий** — какую проблему решаем и для кого (user story).
2. **Границы** — что входит, что осознанно вне скоупа; MVP или полный вариант.
3. **Контракт API** — новые/изменённые endpoints, коды ответов, формат, публичный или внутренний.
4. **Совместимость** — допустимы ли breaking-изменения, миграция и подъём `SCHEMA_VERSION`.
5. **Конфиг/эксплуатация** — нужны ли новые env/CLI-параметры, метрики, документация.
6. **Приоритет и этапность** — тянем в текущую итерацию или только фиксируем план; что делаем первым.
7. **Ограничения** — безопасность, производительность, зависимости (Redis), TLS.
