# Скилл: аудит проекта `dagdb`

Переиспользуемая методика аудита репозитория `yatledger/srv`. Подходит и для первичного аудита
подсистемы, и для **повторного** — с опорой на прошлые находки.

> Аудит **только читает и документирует**. Исходный код (`src/`, `tests/`, `Cargo.toml`, инфраструктура)
> не меняется в рамках аудита; задача — зафиксировать находки и план.

## 0. Как пользоваться

1. Открой сессию в корне репозитория `/home/pin/dev/yat/srv`.
2. Прочитай регламент и контекст (раздел 1).
3. Определи область (весь проект / `src/` / инфраструктура / конкретная подсистема).
4. Проведи анализ по методологии (раздел 3), собери находки.
5. Заведи новую папку `docs/edits/audit/<slug>/` и оформи результат (раздел 4).

## 1. Обязательное чтение перед началом

- [`AGENTS.md`](../../../AGENTS.md) — инварианты, критические зоны, workflow.
- [`docs/README.md`](../../docs/README.md) — карта документации.
- Все существующие аудиты: `docs/edits/audit/*/` (в первую очередь `audit.md` и `tracker.md`) —
  это **реестр уже найденного**, его нельзя дублировать.
- При необходимости — `docs/edits/fix/*/` и `docs/edits/feature/*/` (что уже чинилось/добавлялось).

## 2. История и текущее состояние

- Реестр прошлых находок: аудит **big-bang** в [`docs/edits/audit/big-bang/`](../../docs/edits/audit/big-bang/):
  `audit.md` (находки `S*`/`D*`/`C*`), ТЗ по характерам `01-critical`…`04-missing`, `tracker.md`.
  Все задачи K/V/D/O закрыты — это историческая база, а не активная работа.
- Перед аудитом **сверь фактические статусы трекеров с кодом** (`git log`, дерево) — трекер мог отставать.
- Если прошлые пункты уже закрыты — фиксируй это как прогресс, не переоткрывай.

## 3. Методология

```bash
# 1. Состояние репозитория
git log --oneline -30 && git status

# 2. Собираемость и статический анализ
cargo check
cargo clippy --all-targets

# 3. Тесты
cargo test --all

# 4. «Запахи» кода
grep -rEn '\.unwrap\(\)|\.expect\(|panic!|todo!|unimplemented!' src | wc -l
grep -rn 'TODO\|FIXME\|HACK\|XXX' src
grep -rn 'unsafe' src
grep -rEn 'redis://|http://|password|secret|token' src
```

**Область по умолчанию:** `src/`, `tests/`, `Cargo.toml`, `genesis.json`, инфраструктура
(`Dockerfile`, `docker-compose.yml`, `.github/`, `.env.example`). `docs/legacy/` — черновик,
только отмечай факт наличия, не аудируй по существу.

**Критерии классификации характера (сохраняй преемственность):**

- 🔴 — ломает безопасность/данные/работу, падение узла, утечка секретов.
- 🟠 — серьёзный недочёт, мешает корректной/предсказуемой работе.
- 🟡 — качество/удобство/сопровождаемость.
- 🔵 — важный отсутствующий компонент (тесты, наблюдаемость, спецификация...).

**Особое внимание — инвариантам** (см. `AGENTS.md`, раздел «Инварианты»): канонический хэш/подпись,
детерминированный state machine, `added`/уникальность хэша, разделение публичного/внутреннего API,
контракт Raft-типов.

## 4. Правила работы с находками

1. **Не дублируй** уже зарегистрированные `S*`/`D*`/`C*`. Для них указывай статус:
   «закрыто / частично / не закрыто» со ссылкой на ID и доказательством.
2. Новые находки получают **следующие свободные ID** в своих диапазонах (`S12`, `D10`, `C34`, ...).
   Префиксы: структура `S*`, оформление/доки `D*`, код `C*`.
3. **Не отменяй** ранее принятые решения без явного обоснования и пометки в отчёте.
4. Регрессии (работало и сломалось) помечай отдельно как ⚠️ regression.
5. Каждой находке — характер 🔴/🟠/🟡/🔵 и точная ссылка `файл:строка`.
6. При аудите не меняй `src/`; не удаляй существующие `docs/`; при сомнениях — спрашивай владельца,
   а не домысливай.

## 5. Оформление результата

Создай новую папку: `docs/edits/audit/<slug>/` (например, `docs/edits/audit/security-pass/`).
Рекомендуемое содержимое:

- `audit.md` — находки (таблицы `ID → характер → файл:строка → суть`), обзор области и выводы.
- `tracker.md` — сводный трекер задач со статусами (`⬜`/`🔄`/`✅`) и журналом изменений.
- `NN-<характер>.md` — при необходимости разбивка задач по характерам (🔴/🟠/🟡/🔵), как в big-bang.

В начале каждого документа — пометка группы/типа/статуса, ссылки на соседей — относительными путями.
Добавь папку в `docs/edits/audit/README.md`.

### Формат отчёта аудитора

1. **Сводка:** коммит-база аудита, дата, область, кто проводил.
2. **Прогресс по прошлым аудитам:** таблица `ID → статус (закрыто/частично/не закрыто) → доказательство`.
3. **Новые находки:** таблица `ID → характер → файл:строка → суть → предложение`.
4. **Регрессии:** если есть.
5. **Обновления документов:** какие файлы созданы/изменены.
6. **Открытые вопросы:** что требует решения владельца.
7. **Рекомендация:** что делать следующим и почему.

## 6. Соглашения по ID и трекеру

- Диапазоны ID: структура `S*`, оформление `D*`, код `C*`. ID **не переиспользуются** и не удаляются;
  закрытые сохраняются с пометкой.
- Задачи (в трекере аудита) — свободная нумерация/префиксы по блокам (как `K*`/`V*`/`D*`/`O*`
  в big-bang); новый аудит может выбрать свои понятные префиксы.
- Изменение статусов задач — в `tracker.md` соответствующего аудита, отдельным `docs:` коммитом.
- Коммиты реализации (когда задачи берутся в работу) — Conventional Commits со ссылкой на ID.

## 7. Типовые открытые вопросы владельцу

Проверь и при необходимости уточни (ответы фиксируй в отчёте/ТЗ):

1. **Назначение и зрелость:** внутренний прототип/R&D или движение к production? От этого зависит
   строгость требований (TLS, аудит, соответствие).
2. **Redis:** обязательная зависимость или временное решение? Есть ли план на встроенное хранилище?
3. **`func`:** останется ли один `transferToken` или появится реестр функций/ABI?
4. **Модель `var`:** фиксированная схема (`TxVar`) или произвольный JSON?
5. **Аутентификация узлов:** общий токен, mTLS или подпись запроса ключом узла?
6. **Персистентность `added`:** допустимы ли TTL/лимит или требуется полный реестр?
7. **Приоритеты:** что важнее сейчас — безопасность, производительность, эксплуатация или фичи?
